## 摘要
近期工作将递归自我改进（RSI）扩展到面向长时程编程和终端任务的智能体执行框架（agent harness），使智能体能够从经验中改进执行机制。然而，可泛化的执行框架 RSI 仍具挑战性。首先，在评估基准或其子集上演化执行框架，难以区分可复用的改进与特定于基准的适配。其次，单轨迹更新可能将系统性的执行框架缺陷与实例特定的推理和解题细节混为一谈，从而产生难以迁移到未见任务的修改。第三，在单体式执行框架中定位反复出现的行为缺陷十分困难，而整体执行框架优化可能纠缠无关机制，并使归因和验证复杂化。我们提出 ModularRSI，一个面向可泛化执行框架演化的、与基准不相交的、对比式且模块化的框架。ModularRSI 对比同一任务的成功与失败轨迹，并跨任务聚合证据，以识别反复出现的行为缺陷。它将可演化的执行框架分解为五个功能模块：Agent Loop、Tool Use、Observation Management、Context Management 和 Task Completion Detection。每个模块在受限修改范围内独立演化，随后进入集成阶段，将演化后的模块组合为统一的执行框架并解决潜在冲突。为支持与基准不相交的演化，我们从外部来源精心构建了 2,000 个可执行演化任务，这些任务与下游评估基准不相交。在 TB2.0 和 SWE-Bench Verified 上的实验表明，在未见的域内和跨域任务上均取得一致改进，且演化后的执行框架还能迁移到不同的基础模型。

## Abstract
Recent work extends recursive self-improvement (RSI) to agent harnesses for long-horizon coding and terminal tasks, enabling agents to improve execution mechanisms from experience. However, generalizable harness RSI remains challenging. First, evolving harnesses on evaluation benchmarks or their subsets makes it difficult to distinguish reusable improvements from benchmark-specific adaptation. Second, single-trajectory updates can conflate systematic harness deficiencies with instance-specific reasoning and solution details, producing modifications that transfer poorly to unseen tasks. Third, localizing recurring behavioral deficiencies within monolithic harnesses is difficult, while whole-harness optimization can entangle unrelated mechanisms and complicate attribution and validation. We propose ModularRSI, a benchmark-disjoint, contrastive, and modular framework for generalizable harness evolution. ModularRSI contrasts successful and failed trajectories for the same task and aggregates evidence across tasks to identify recurring behavioral deficiencies. It decomposes the evolvable harness into five functional modules: Agent Loop, Tool Use, Observation Management, Context Management, and Task Completion Detection. Each module evolves independently within a restricted modification scope, followed by an integration stage that combines the evolved modules into a unified harness and resolves potential conflicts. To support benchmark-disjoint evolution, we curate 2,000 executable evolution tasks from external sources that are disjoint from downstream evaluation benchmarks. Experiments on TB2.0 and SWE-Bench Verified show consistent improvements on unseen in-domain and cross-domain tasks, with the evolved harness also transferring across different foundation models.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：CLI 智能体在复杂软件工程与终端任务上表现突出，其效果越来越依赖 **agent harness**（执行框架）——负责执行流程、工具交互、上下文管理与环境反馈。近期研究将**递归自我改进（RSI）** 扩展到 harness，使智能体从执行经验中改进执行机制。
- **核心问题**：可泛化的 harness RSI 仍面临三个耦合挑战：
  - **数据层面**：现有方法通常在评估基准或其子集上演化 harness，难以区分"可复用改进"与"基准特化适配"；高质量、可执行、多样化的演化数据构建成本高。
  - **轨迹层面**：单条或单侧轨迹会混淆**系统性 harness 缺陷**与**实例特定推理/解题细节**，导致修改难以迁移到未见任务。
  - **机制层面（信用分配问题）**：即使识别出反复出现的行为缺陷，也难以定位到单体式 harness 中应修改的组件；整体优化会纠缠无关机制，使归因与验证困难。
- **整体含义**：论文主张通过**基准不相交（benchmark-disjoint）+ 对比式（contrastive）+ 模块化（modular）** 的 harness 演化，将粗粒度任务级结果转化为局部化的 harness 修改信号，从而获得可复用、可归因、可跨任务与跨模型泛化的能力提升。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
- 将 harness 的行为机制分解为**五个可独立演化的功能模块**，利用**同一任务的成功/失败轨迹对比**识别缺陷，并通过**跨任务证据聚合**过滤实例特定噪声，最后经**验证门**与**跨模块整合**形成统一 harness。

### 2.2 三大阶段流程
1. **对比轨迹采样与分析**
   - 对每个演化实例 $x_i$ 进行 $K$ 次 rollout，得到轨迹集 $(tra_i^1,\dots,tra_i^K)$，由任务专属评估器给出二值奖励 $r_i^k \in \{0,1\}$。
   - 按奖励将任务分为三组：
     - **Positive**：$\sum_k r_i^k = K$（全成功）
     - **Contrastive**：$0 < \sum_k r_i^k < K$（成功失败混合）
     - **Negative**：$\sum_k r_i^k = 0$（全失败）
   - 维护 **Trajectory Memory**，存储历史轨迹及奖励；对 Negative 组可回溯历史成功轨迹与当前失败轨迹配对。
   - 分析模式：
     - **Contrastive**：同任务成功/失败轨迹配对，找函数级差异因素；
     - **Negative**：优先历史成功配对，否则做单侧诊断（重复循环、错误工具使用、无效恢复、过早终止等）；
     - **Positive**：关注效率与执行质量（冗余动作、重复探索、不必要工具调用）。
   - 输出结构化 JSON findings，包含：所属模块、轨迹证据、修改理由、建议改动。

2. **模块化 harness 修改**
   - **Modification Target Selection**：合并语义相近的诊断，按**支持任务数投票**排序，优先跨任务支持的修改。
   - **Evolution History**：为每个函数记录历史改动，避免重复/冲突修改与演化震荡。
   - 五个模块独立并行演化，互不共享中间更新。

3. **验证门（Validation Gates）**
   - **Program Check**：AST 校验、import 检查、协议合规、发现契约验证、静态自属性审计；失败则回滚。
   - **Diff Review**：让 Code-Modify Agent 审查 diff，拒绝编码任务特定解、启发式或难以泛化的条件。
   - **Execution Validation**：每批随机抽 2 个任务实际执行，若引入运行错误或违反执行协议则回滚。

### 2.3 五个功能模块
| 模块 | 职责 |
|---|---|
| **Agent Loop** | 迭代式推理–行动–观察流程、执行流控制、交互控制、恢复行为 |
| **Observation Management** | 处理环境反馈，保留任务相关信息、过滤/压缩噪声 |
| **Tool Use** | 外部工具的选择、调用与验证 |
| **Context Management** | 维护和整理跨步交互历史（信息保留、压缩、检索） |
| **Task Completion Detection** | 判定任务是否完成或需继续交互 |

### 2.4 跨模块整合与函数库管理
- **Cross-Module Integration**：独立演化的模块组合后，做一轮集成 epoch，识别跨模块冲突，去重、明确职责、调整协调逻辑；之后函数库**冻结**。
- **Function Merge**：LLM 比较模块内函数描述与行为，合并高度相似者。
- **Task-Aware Function Composer**：根据任务描述与函数描述，由 LLM 选择任务相关子集激活，保持活跃 harness 紧凑。

### 2.5 演化数据构建协议
- 从 TerminalBench / SWE-Bench 家族提取高层领域标签作为**检索引导**，从 GitHub、Hugging Face、Kaggle、Linux 内核文档等外部来源构造 2,000 个可执行任务。
- 多阶段质控：LLM 过滤（环境完整性、实用性/非平凡性、评估器有效性）→ 可执行验证（参考解通过、no-op 不得分）→ 人工审查 → LLM 语义相似度筛选（去除与下游基准重叠）。
- 数据分布相对均衡，涵盖 Data processing、ML & science、Build & deps、Systems & OS、Lang & API、Web & network、Algorithms、Security & crypto、Database 等 9 类。

## 6. 主要结论与发现

- **跨基准泛化**：TB 相关演化使 SWE-Bench Verified Acc 从 73.40 → **75.80**；SWE 相关演化使 TerminalBench 2.0 Acc 从 47.57 → **49.40**；同域演化分别提升至 **52.43** 与 **76.45**。
- **可靠性提升**：TerminalBench 2.0 上 Pass3 从 30.34 → **35.96**，说明不仅平均能力提升，重复试验的稳定性也增强。
- **跨模型迁移**：冻结的 harness 在 GLM-5.2（59.55 → 61.80）、MiniMax-2.5（41.57 → 44.94）、DeepSeek-V4-Flash（47.57 → 52.43）上均一致提升。
- **模块化优于联合/非模块化**：Non-modular（46.44）与 Joint All-Module（44.19）均低于基线，而 ModularRSI 达 **52.43**，说明限制修改范围可减少干扰。
- **单模块互补**：Agent Loop 带来最大单模块 Acc 增益（50.56）；Observation Management 显著降低步数（34.70 → 22.50）；整合后 Acc 52.43、Pass3 35.96。
- **优于现有 RSI 方法**：在基准不相交协议下，AHE 与 Meta-Harness 仅约 ±1 个百分点变化，而 ModularRSI 提升超过 **5 个百分点**（61.79 → 67.42）。
- **对比对随演化递减**：contrastive pair 比例从 36.67% 降至 34.17%（Δ = -7.50 pp），说明可复用改进被逐步吸收。
- **数据难度影响**：Medium-centered 分布演化出的 harness 在 SWE-Bench Verified 上达 **76.45%**，优于 Hard & Easy 的 74.25%（+2.20 pp）。

## 7. 优点

- **基准不相交协议**：从外部来源独立构建 2,000 个可执行演化任务，并经相似度筛选，严格与下游基准解耦，能真实检验泛化而非基准特化。
- **对比式信用分配**：同任务成功/失败轨迹配对 + 跨任务证据聚合 + Trajectory Memory 回溯，有效将粗粒度任务结果转化为函数级信号，并抑制实例特定噪声。
- **模块化设计**：五模块分解 + 受限修改范围 + 独立并行演化 + 跨模块整合，缓解了单体 harness 优化中的机制纠缠与归因困难。
- **多重验证门**：Program Check、Diff Review（反过拟合）、Execution Validation 三道关卡保证修改可执行且不过拟合。
- **函数库管理**：Function Merge + Task-Aware Composer 兼顾库扩展与活跃 harness 紧凑性。
- **实验维度丰富**：跨域、跨模型、模块消融、方法对比、数据难度、演化曲线等多角度验证，结论相互支撑。
- **实践价值**：演化后的 harness 可冻结并跨模型迁移，具备实际部署复用价值。
