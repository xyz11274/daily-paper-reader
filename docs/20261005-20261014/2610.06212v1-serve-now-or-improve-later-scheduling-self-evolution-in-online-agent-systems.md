## 摘要
在线智能体可以通过构建可复用的工具、指导或模型状态来改进未来服务，但这项工作会与当前请求争夺相同的GPU。利用空闲算力进行自演化面临一个根本性的系统约束：收益只有在产物发布并被使用后才会到来，而暂停演化则会让服务容量等待内存释放和运行时恢复。因此，一项值得完成的投资可能也值得推迟。我们提出LearnSched，一种状态感知调度器，它将能力的复用窗口与算力的及时返回纳入统一的投资模型。LearnSched将候选进度、检查点开销和当前恢复路径纳入动作价值。在相同的信息和容量约束下，它使用一步反事实推演，相对于完全计价的窗口策略来选择推进、检查点或等待。我们通过独立的A100组件测量来刻画交接成本，并在1920个配对的有限模型场景中评估动作选择。当冷恢复代价高昂时，等待更长的执行窗口可以通过避免交接来提高净价值；在评估的温恢复场景中，强窗口策略已经实现了相同的价值。保留可恢复状态可以缩短容量返回时间，并减少对复杂演化调度的需求。

## Abstract
Online agents can improve future service by constructing reusable tools, guidance, or model states, but this work competes with current requests for the same GPUs. Exploiting idle compute for self-evolution faces a fundamental systems constraint: benefits arrive only after an artifact is published and used, while pausing evolution leaves service capacity waiting for memory release and runtime recovery. An investment worth completing may therefore be worth postponing. We present LearnSched, a state-aware scheduler that brings the reuse window of a capability and the timely return of compute into a common investment model. LearnSched incorporates candidate progress, checkpoint overhead, and the current recovery path into action values. Under the same information and capacity constraints, it uses one-step counterfactual rollout to choose progress, checkpointing, or waiting relative to a fully costed window policy. We characterize handoff costs through independent A100 component measurements and evaluate action selection in 1920 paired finite-model scenarios. When cold recovery is expensive, waiting for longer execution windows can improve net value by avoiding handoffs; in evaluated warm-recovery scenarios, the strong window policy already achieves the same value. Retaining recoverable state can shorten capacity return and reduce the need for complex evolution scheduling.

## 1. 核心问题与整体含义

- **研究动机**：在线智能体（如编码智能体）可以通过构建可复用工具、指导或模型状态来提升未来服务质量，但这一"自演化"过程与当前用户请求共享同一批 GPU，形成算力竞争。
- **根本矛盾**：自演化的收益具有**滞后性**——只有产物发布并被后续请求实际使用后才产生价值；而暂停演化以归还算力时，又需经历内存释放与运行时恢复的延迟，导致"算力归还"并非即时事件。
- **核心问题**：在服务与演化共享 GPU 的在线系统中，系统应当"立即服务"还是"稍后改进"？一项值得完成的投资，是否也值得**现在就开始**？
- **整体含义**：论文指出，演化调度的关键不只是"是否投资"，而是**何时投资、何时暂停、何时归还算力**。恢复路径（冷启动 vs 热恢复）与状态保留策略会显著改变最优执行计划，因此运行时内存管理与投资调度必须联合评估。

## 2. 方法论

### 2.1 核心思想
- 将在线自演化视为一种**带延迟回报的算力投资**，把"能力复用窗口"与"算力及时归还"纳入统一的投资模型。
- 提出 **LearnSched**：一个状态感知调度器，通过一步反事实推演（one-step counterfactual rollout），在"推进工作、检查点并归还、丢弃未保存工作、等待"之间做选择。

### 2.2 状态与动作建模
- **状态定义**：\( s_t = (m_t, p_t, \bar{p}_t, z_t, q_t) \)，其中 \( m_t \) 为服务/演化模式，\( p_t \) 为已完成进度，\( \bar{p}_t \) 为持久化进度，\( z_t \) 为驻留服务状态及恢复路径，\( q_t \) 为前台积压。
- **动作空间**：等待、推进工作、检查点并归还、丢弃未保存工作并归还；动作需满足**容量归还约束** \( \mathcal{A}_{ret}(s, \mathcal{I}_t) \)。
- **价值函数**：\( V^*_t(s) = \max_{a \in \mathcal{A}_{ret}} \{ r(s,a) - c(s,a) + \mathbb{E}[V^*_{t+\tau}(s') \mid s, a, \mathcal{I}_t] \} \)，收益仅在产物发布并使用后产生，成本仅计入当前动作的执行、检查点、恢复与驻留开销。

### 2.3 关键分析工具
- **有效复用与盈亏平衡**：定义 \( V(t) = M(t)u - C_e \)，其中 \( M(t) = \lambda a (H - t - \tau_e)^+ \)，导出正回报的启动截止时间 \( t^*_e = H - \tau_e - \frac{C_e}{\lambda a u} \)。
- **请求截止期与可借出容量**：基于 FIFO 流体队列模型，给出及时完成条件 \( \sum_{j=k}^{i} w_j \leq \int_{a_k}^{d_i} c_{cap}(v) dv \)，并定义 \( B_{ki} \leq S_{ki} + R_{ki} \)（容量损失 ≤ 基线容量 + 避免的工作）。
- **状态相关归还截止期**：\( \tau_r = \tau_{act} + \tau_{release} + \tau_{ready} \)，要求 \( t_{reclaim} \leq t_b - \tau_r \)。
- **等待价值**：\( V_{wait} - V_{now} = (C_1 - C_2) - g(t_2 - t_1) \)，即等待节省的交接/检查点成本与延迟损失的收益之差。

### 2.4 调度算法
- **参考策略 Costed Window (\( \pi_0 \))**：贪心完成计划，对所有剩余收益与成本（含交接成本）完全计价，若完成价值高于放弃则执行，否则等待并重新评估。
- **Rollout 决策**：\( Q_{\pi_0}(s,a) = r(s,a) - c(s,a) + V_{\pi_0}(s') \)，在候选动作中取最大，平局时保留参考动作，每个窗口重新计算。
- **理论保证（命题1）**：在有限阶段、准确转移/成本/参考值且 \( \pi_0(s) \) 安全的条件下，\( V_{\pi_R}(s) \geq V_{\pi_0}(s) \)；若评分误差有界 \( |\hat{Q} - Q_{\pi_0}| \leq \epsilon \)，仅接受 \( \hat{Q}(s,a) > \hat{Q}(s,\pi_0) + 2\epsilon \) 的改动可保证真实分数不下降。
- **计算复杂度**：枚举至多 \( K \) 个剩余窗口上的 \( O(J) \) 进度预算，对相同持久进度缓存续值；精确 DP 给出模型最优解。

## 6. 主要结论与发现

- **等待可以是有价值的**：当冷恢复代价高昂时，等待更长的执行窗口可避免一次检查点和一次冷恢复，从而提升净价值。典型案例中，延迟发布 4.952 s 节省 70.104 s-eq. 的执行与交接成本，净增益 68.866 s-eq.。
- **热恢复削弱调度优势**：在所有 960 个热恢复场景中，LearnSched 与 Costed Window 打平；复杂规划的价值被状态保留所替代。
- **完整成本记账解释大部分收益**：Costed Window 的平均 DP 差距为 5.369 s-eq.，而 rollout 仅 0.246 s-eq.，rollout 相对 Costed Window 的平均增益为 5.123 s-eq.（1.10%），91 个场景改进、1829 个打平、0 个退步。
- **状态保留改变容量归还**：热恢复将就绪时间从 69.99 s 降至 0.487 s，但主机 PSS 从 4.77 GiB 升至 11.16 GiB，GPU 保留 3.74 GiB；保留状态以内存换速度。
- **资源定价影响盈亏平衡**：同一构建在 token 定价下需 2–3 次使用即可回本，在 GPU 活跃时间定价下需 5–80 次；TokenROI 比 Never 少用 73.76% token 但多用 86.23% GPU 活跃时间。
- **就绪不等于使用**：LearnSched 的指导产物使用/就绪比为 50.9%（vLLM）和 42.7%（SGLang），高于 Eager 的 37.8% 和 32.2%；将每个发布后请求计为复用会高估摊销。
- **提前通知的价值**：预通知扩展使突发错过率为 0%，反应式扩展为 44.0%，无扩展为 65.4%；但提前返回的收益取决于告警置信度与提前时间，误报成本需计入。

## 7. 优点

- **问题建模新颖**：将自演化调度形式化为带延迟回报和状态相关切换成本的投资问题，明确区分"完成投资"与"现在开始投资"。
- **理论严谨**：给出盈亏平衡条件、容量归还约束、rollout 策略改进命题及评分误差下的保守接受条件。
- **实验设计精细**：配对有限模型 + 独立组件测量 + 能力账本三层分离，有效隔离记账收益与调度收益；Exact DP 提供最优基准。
- **系统洞察实用**：揭示"热恢复使复杂调度变得不必要"这一反直觉结论，对运行时设计与调度策略的联合优化具有指导意义。
- **成本核算全面**：区分 token、GPU 活跃时间、主机内存三种资源，并显式定价，避免单一指标误导。

## 8. 不足与局限

- **实验覆盖有限**：有限模型基于合成能力与合成日历，未覆盖多候选、多资源类型、真实生产到达过程；部分实验仅 1 次运行，尾部风险未刻画。
- **在线验证缺失**：告警决策使用合成事件，未验证在线预测精度；需求轨迹为模拟，非真实部署测量。
- **模型简化**：内存定价为假设值（0.01 s-eq./GiB-second），未测量进入/释放延迟，未拟合驻留内存对吞吐的影响；CPU 成本单独计时但未纳入统一优化。
- **维护成本未计**：未系统考虑能力版本更新、失败检测、重新验证等长期维护成本，也未建模能力随任务变化而衰减。
- **信息假设较强**：Cal.* 拥有未来到达日历，属于信息上界而非可实现策略；LearnSched 的在线估计误差界未经验证。
- **应用限制**：结论依赖于具体恢复路径（冷/热）与资源定价，迁移到其他硬件、模型或工作负载时需重新校准。
