## 摘要
智能体可以完成任务，却不改进其工作方式。要将任务经验转化为可复用的能力，需要将被改变的组件与其评估及后续使用连接起来。我们提出 AgentEvolver，一个在保持基础模型固定的同时，在任务执行过程中发展能力的系统。八个实体族通过一个通用的版本化生命周期，将可复用操作、方法、智能体、控制流、接口和支持状态暴露给修订。一个共享的运行时协调正在进行的工作，而持久化规划和可恢复上下文则保留任务方向与支持性证据。我们在 SWE-bench Pro Public 上评估任务结果，并在六个应用案例中考察能力变化。团队报告称，在进化条件下解决率达到 82.08\%，超过其报告的无进化基线。这些案例显示，保留下来的能力进入了后续的网站、游戏和研究工作，同时也记录了未完成的目标和一次不成功的策略。这些发现将可复用组件的改进与最终任务上的成功区分开来。AgentEvolver 为研究通过执行实现能力积累提供了具体基础；独立任务迁移和总开发成本仍是未决问题。

## Abstract
An agent can complete a task without improving how it works. Turning task experience into reusable capability requires connecting the changed component to its evaluation and subsequent use. We present AgentEvolver, a system for developing capabilities during task execution while keeping the foundation model fixed. Eight entity families expose reusable operations, methods, agents, control flow, interfaces, and supporting state to revision through a common versioned lifecycle. A shared Runtime coordinates ongoing work, while persistent planning and recoverable context preserve task direction and supporting evidence. We evaluate task outcomes on SWE-bench Pro Public and examine capability changes in six application cases. The team reports an 82.08\% resolution rate with evolution, exceeding its reported baseline without evolution. The cases show retained capabilities entering later website, game, and research work, while also documenting incomplete objectives and an unsuccessful strategy. These findings distinguish improvement in a reusable component from success on the final task. AgentEvolver provides a concrete basis for studying capability accumulation through execution; independent-task transfer and total development cost remain open questions.

## 1. 核心问题与整体含义

- **研究动机**：当前智能体（Agent）能够完成具体任务，但完成任务的过程本身并不会自动改进其工作方式。任务经验难以沉淀为可复用的能力，导致每次面对类似问题时需要从头开始。
- **核心痛点**：要将任务经验转化为可复用能力，必须将被修改的组件与其评估过程、以及后续的实际使用连接起来。现有方法（如 ReAct、Reflexion、Voyager）虽然能让经验存在于模型参数之外，但缺乏对"改动—评估—留存—使用"这一完整链路的统一管理。
- **整体含义**：论文提出 **AgentEvolver**，一个在**保持基础模型固定**的前提下，于任务执行过程中发展能力的系统。其核心主张是：能力演化不应只关注生成一个新工具，而必须连接"变更的身份、测试变更的执行、以及变更被消费的任务状态"。
- **概念界定**：作者提出"**全局能力演化（global capability evolution）**"概念——Tool、Skill、Agent、Workflow、Connector、Environment、Memory、Plugin 八类组件可以变化，而基础模型保持不变。"全局"指的是工作系统的适应面，而非最优搜索保证。

## 2. 方法论

### 2.1 核心思想

- 将任务执行状态形式化为六元组：**St = (Dt, Lt, At, Rt, Ht, bt)**，其中 Dt 为交付物状态，Lt 为已接纳组件版本档案，At 为活跃版本映射，Rt 记录流程/调用/所有权，Ht 为规划与交互记录，bt 为剩余预算。
- 区分**普通任务动作**（使用活跃能力改变交付物）与**演化动作**（新增归档版本、改变活跃选择、追加评估与决策记录），二者共享 Runtime 与预算核算。
- 三条设计需求：**身份（Identity）**必须跨后续编辑存活；**连续性（Continuity）**必须保留任务方向与执行所有权；**证据（Evidence）**必须将留存决策连接到实际观察与后续使用。

### 2.2 八类演化面与变更单元

- 八类组件族：Tool（可执行操作与输入模式）、Skill（方法/检查/脚本/参考）、Agent（行为/提示/配置）、Workflow（结构化可执行控制流）、Connector（面向提供方的动作与契约）、Environment（观察/状态/动作接口）、Memory（留存与检索实现）、Plugin（服务实现与相关工具）。
- 共享身份为元组 **(f, n, v)**：族、注册名、版本。组件定义、其实例、其存储内容必须可区分——例如派发新 worker 不改变 Agent 定义，写故障记录是 Memory 内容更新而非 Memory 组件演化。

### 2.3 Runtime：能力变化中协调工作

- 分离**持久 Agent 进程**（拥有对话、邮箱、子工作）与**有界组件调用**（记录操作与结果）。
- 所有操作通过统一调用边界，记录所有者、父调用、组件身份、执行状态；声明式共享/独占资源声明控制冲突访问。
- 生命周期状态：NEW、RUNNING、IDLE、SUSPENDED、STOPPING、EXITED；父进程退出前必须停止并 join 子进程。
- 根运行及其后代共享资源核算，候选构建、失败尝试、评估与实际消费均计入原任务成本。

### 2.4 Plan 与 Context：保留方向与证据

- **Plan**：紧凑索引（限 2,000 字符）链接到详细记录（目标、验收标准、依赖、决策）；最新索引在模型请求前注入，支持记录按需检索。
- **Context**：分层上下文管理，组合稳定指令、检查点摘要、近期完整交互；压缩时保留归档，并检查候选摘要是否真正减小完整请求，否则恢复原始历史。
- **Trace**：记录有效模型请求、调用动作、返回观察，与版本档案共同支持留存决策的事后重建。

### 2.5 从观察到留存能力的生命周期（六步协议）

1. **观察**任务限制，保留基线调用，定义面向消费者的验收标准。
2. **编写**候选并注册其精确的族、名、版本；若准入失败则保留失败并修订或放弃。
3. **评估**已准入候选（对比基线与回归用例），收集实际调用标识与观察结果。
4. 若证据缺失、版本不匹配或必需用例失败，**不记录通过的 keep**；修订、恢复先前版本或卸载。
5. 记录**受支持的决策**并单独执行状态变更操作；保留归档载荷与决策历史。
6. 在后续任务工作中**使用**留存版本，记录消费者与产物；最终交付物独立评估。

- **关键区分**：结构准入、功能评估、采纳、后续使用是四个不同事件，一个事件的证据不能确立其他事件发生。

## 6. 主要结论与发现

- **RQ1（编码任务结果）**：团队报告进化启用时解决率 82.08%，无进化时 79.07%，绝对差 3.01 个百分点，净增 22 个解决任务。该对比支持进化启用条件。
- **RQ2（能力变更如何进入后续工作）**：三个跨案例模式：
  1. **语义失败驱动有用修订**：ORBITAL 的源日期错误、Godot 的字体实际权重、LUMEN 对历史观察的解释，暴露了语法或模式验证遗漏的缺口。
  2. **后续消费者是连接任务工作的纽带**：影响追踪、路线审查、引擎诊断、冻结重放各自在初始比较后进入已识别的操作。
  3. **局部改进可与未达成目标共存**：ORBITAL 缺少必需的 review 组件、Godot 仍是未完成的游戏、Signal Foundry 选定策略未达比较标准。
- **核心区分**：可复用组件的改进 ≠ 最终任务的成功。留存一个有用组件不证明任务完成，完成交付物也不证明可复用组件改进。
- **开放问题**：独立任务迁移、总开发成本回收、无约束下的变更面选择、压缩的语义完整性、恢复可靠性等仍需针对性研究。

## 7. 优点

- **概念清晰**：明确区分交付物状态、归档版本、活跃版本、评估证据与后续使用，避免了"可用性即改进"的常见混淆。

- **实验覆盖有限**：
