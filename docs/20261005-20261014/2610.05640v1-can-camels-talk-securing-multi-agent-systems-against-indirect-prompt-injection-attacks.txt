Abstract —Indirect prompt injection attacks – malicious in-structions embedded in content processed by large language models – remain a major obstacle to safely deploying tool-using agents. CaMeL [1] mitigates this threat for an individual agent by separating trusted control flow from untrusted data and enforcing capability-based security policies at runtime. In this work, we investigate whether CaMeL’s security guarantees compose in hierarchical multi-agent systems, where agents invoke other agents as tools. We find that CaMeL’s guarantees do not compose. We construct a concrete prompt-injection attack that succeeds despite all constituent agents individually operating CaMeL. Our attack exploits the fact that untrusted data can be reinterpreted as trusted input by a downstream agent. We then introduce multi-CaMeL, an agent-to-agent communication protocol that preserves provenance across agent boundaries by separating trusted natural-language instructions from untrusted data passed through a distinct data channel. We evaluate multi-CaMeL’s utility on AssetOpsBench and its security-utility trade-off on MultiAgentDojo, a benchmark we develop by extending AgentDojo to the multi-agent setting. We find that multi-CaMeL reduces attack success rate (ASR) to 0.0%, compared with 0.2% for individual-agent CaMeL and 12.9% with no CaMeL. Multi-CaMeL incurs a utility cost, but this cost trends downward as model capability increases and is modest for the strongest models, suggesting that more capable models better accommodate the constraints imposed by the protocol. 

I. I NTRODUCTION 

Prompt injection is a class of attacks in which adversaries craft inputs that cause large language models (LLMs) to follow unintended instructions. When these instructions are supplied directly by the user, this is known as direct prompt injection. In an indirect prompt injection attack, however, the instructions are embedded by an adversary in external content – such as webpages, emails, or documents – that an LLM processes 

indirectly while performing a task. As LLM-based agents are increasingly deployed in real-world environments and granted access to external data sources, tools, and services, the attack surface for indirect prompt injections expands significantly. An adversary may, for example, place malicious instructions in an email or webpage that is later retrieved and processed by an agent. Prior work has demonstrated concrete indirect prompt injection attacks [2] and documented the prevalence of prompt injection content in the wild, including on publicly accessible webpages and other real-world online sources [3]. Existing defenses against indirect prompt injection can be categorized by the stage of the agent’s processing pipeline

at which they intervene. Model-level defenses modify the backend LLM at training time – typically through fine-tuning or preference optimization. The model learns to distinguish privileged instructions from lower-authority content and resist following injected instructions [4, 5]. Input-level defenses leave the backend LLM unchanged and instead filter, trans-form, or restructure its context at inference time. DataFilter, for example, uses a separately trained filtering model, conditioned on both the user instruction and the untrusted data, to remove adversarial instructions while preserving task-relevant content [6]. Similarly, prompt sanitization techniques repeatedly in-spect incoming data and rewrite, mask, or remove instruc-tions that could compromise agent behaviour [7]. Prompt-structuring techniques provide a lighter-weight alternative: sandwich prompting restates the trusted task after the untrusted content [8], while spotlighting marks or encodes untrusted text to make its provenance more salient to the model [9]. Although these approaches can often be integrated into existing agent pipelines, they generally rely on learned model behavior and do not provide hard security guarantees [10]. System-level defenses enforce security outside the LLM through structural mechanisms such as privilege separation, information-flow tracking, sandboxing, and policy checks on tool use. One such approach is Willison’s Dual LLM pat-tern [11], which separates the agent into a Privileged LLM (PLLM) and a Quarantined LLM (QLLM) . The PLLM receives only trusted instructions and determines the actions required to complete the user’s request – for example, locat-ing meeting notes in Google Drive and sending a summary to a specified employee – but is prevented from directly observing the untrusted contents of those notes. Tasks that require processing untrusted data, such as summarization, are delegated to the QLLM. Because the QLLM has no access to privileged tools, an injected instruction cannot directly cause it to perform sensitive actions. This Dual LLM pattern separates the agent’s control flow – the sequence and selection of actions it takes – from the processing of untrusted data. As a result, untrusted content may influence the QLLM’s output, but it cannot directly determine which privileged actions or tool calls the agent performs. CaMeL [1] is a concrete instantiation of the Dual LLM pattern. It leverages the code-generation capabilities of modern LLMs: a Privileged LLM expresses the agent’s trusted control flow as a Python program, and delegates the processing of untrusted data to a separate Quarantined LLM. Evaluations on AgentDojo [12] show that CaMeL substantially outperforms tool filtering, spotlighting, and prompt sandwiching in security, while im-posing a comparatively modest utility cost. CaMeL is not the only system-level approach to securing LLM agents; recent work has also explored information-flow control [13, 14] and fine-grained privilege enforcement [15]. We focus on CaMeL because it explicitly separates trusted control flow from untrusted data, has demonstrated a strong empirical se-curity–utility tradeoff, and is likely to incur lower utility costs as the code-generation and planning capabilities of frontier models improve. CaMeL is formulated for a single agent interacting with its environment. This leaves open an increasingly important setting: multi-agent systems. Such systems can take a variety of forms, including peer-to-peer, collaborative, competitive, and hierarchical structures. One increasingly common form is the multi-agent orchestrator pattern, where a central agent delegates subtasks to specialized sub-agents [16, 17]. Recent work demonstrates the use of multi-agent architectures for complex end-to-end workflows; for example, FORGE coordi-nates five specialized agents in a fixed pipeline for vulnerabil-ity assessment, exploitation, and detection engineering [18]. At the same time, interactions between agents can introduce security concerns that are inherently multi-agent: Rose et al. study covert collusion between LLM agents and show that its detection can require aggregating signals across agents rather than considering each agent independently [19]. These developments motivate asking whether security guarantees established for individual agents continue to hold when agents communicate and delegate tasks within a larger system. In this work, we examine how CaMeL’s security guarantees extend to multi-agent systems. We show that securing each agent individually with CaMeL does not suffice to preserve these guarantees at the system level. In particular, data treated as untrusted by one agent may cross an agent boundary and be presented to a downstream agent as trusted input. An attacker can therefore exploit the boundary between individually secure agents: an indirect prompt injection encountered by one agent may influence the control flow of another, compromising the system as a whole. We refer to this failure mode as boundary laundering and demonstrate it empirically with a concrete multi-agent prompt-injection attack. To address this, we introduce multi-CaMeL, an extension of CaMeL to hierarchical multi-agent systems that preserves provenance across agent boundaries. Rather than allowing parent agents to freely embed tool-derived values into the natural-language instructions passed to child agents, multi-CaMeL separates such communication into a trusted instruc-tion channel and a distinct channel for values derived from untrusted data. The child agent’s PLLM therefore receives only trusted natural-language instructions, while untrusted values remain opaque to it and are accessed separately at runtime. 

A. Contributions 

Our main contributions are: 1) We formalize security in hierarchical multi-agent sys-tems with the agent-as-tool pattern (agents invoking other agents via tools), and characterize when control-flow integrity of individual agents composes to the system level. 2) We show that individual CaMeL security does not, in general, compose. We construct a concrete prompt-injection attack which succeeds via boundary laun-dering: all constituent agents are individually CaMeL-secure, yet untrusted data is reinterpreted as trusted input by a downstream agent and hijacks its control flow. 3) We introduce multi-CaMeL, a multi-agent extension of CaMeL that preserves provenance across agent bound-aries by separating trusted natural-language instructions from untrusted data and propagating security metadata between agents. 4) We introduce MultiAgentDojo as an extension of Agent-Dojo [12] to hierarchical multi-agent systems. We eval-uate multi-CaMeL empirically, and present the secu-rity–utility tradeoff of no CaMeL, individual CaMeL, and multi-CaMeL on MultiAgentDojo and AssetOps-Bench [20] across 5 backend LLMs from different model families and capability levels. II. F ORMAL SETUP 

A. Hierarchical Agent-as-Tool Systems 

We study a restricted class of multi-agent systems in which agents are arranged hierarchically and interact through the agent-as-tool pattern: parent agents invoke child agents via tool calls, and each child agent treats its invoking parent as its user. We refer to these as hierarchical agent-as-tool systems . We focus on this class for two reasons. First, hierarchical agent-as-tool architectures are increasingly common in contempo-rary agent systems, particularly in settings where a central orchestrator delegates tasks to specialized sub-agents via tool calls [16, 21]. Second, their hierarchical structure provides explicit parent–child boundaries and a well-defined direction of information flow, enabling us to state and analyze security properties precisely. Hierarchical agent-as-tool systems have also been studied as an attack surface in prior work on multi-agent security [22]. We discuss in Section VI how the findings of this paper may extend beyond this class of multi-agent systems.

B. Control Flow Integrity in Agents and Multi-Agent Systems 

In systems security, control-flow integrity (CFI) is the property that the execution of a program can only follow paths permitted by a predefined security policy [23], limiting an attacker’s ability to divert execution from its intended behaviour. We adapt this notion to tool-calling agents and multi-agent systems. In these systems, the relevant control flow is the sequence and selection of tool invocations made during execution. 

Definition 2. A control-flow plan is a prespecified program that, as a function of intermediate tool return values and computations, deterministically specifies the sequence and selection of tool invocations made during execution. 

Definition 3. A tool-calling agent A, or multi-agent system 

M, satisfies control-flow integrity (CFI) if its execution is con-fined to a control-flow plan determined by the user instruction and other trusted information, such as tool or environment descriptions. CaMeL satisfies CFI in the single agent setting: seeing only the user instruction u and environment descriptions, the agent’s PLLM generates a Python program specifying the control-flow plan which the agent then adheres to. In particular, untrusted data returned by tools may affect the branches selected among those already present in the plan, but cannot introduce new control-flow paths. In addition to CFI, CaMeL also enforces security policies to the data passed into tool calls. A security policy S decides whether given tool invocations are permitted based on their arguments and on the capabilities associated with those arguments and their dependencies. For example, a policy may prohibit send_email 

from being called with arguments that are derived from private data to a recipient who is not authorized to read that data. These policies protect against data-flow attacks, in which an attacker, despite being unable to alter the agent’s control flow, can still influence data produced by the QLLM within an otherwise valid plan, causing unauthorized actions such as the exfiltration of sensitive information. 

Definition 4. A tool-calling agent A or multi-agent system 

M is CaMeL-secure under security policy S if the system satisfies CFI and S is enforced globally on tool calls. Under our definitions, CFI is equivalent to CaMeL-security under the trivial security policy ( S = ∅). In our experiments, we study CaMeL agents configured with no security policies. We do this for two reasons. First, showing that CFI fails to compose is sufficient to show that CaMeL-security fails to compose in general. Second, configuring non-trivial policies would require making arbitrary choices among many possibilities, and any security or utility results would be dependent on the particular policies enabled. Section IV discusses how our Multi-CaMeL extends naturally to the case where we require non-trivial security policies. III. L IMITS OF INDIVIDUAL AGENT SECURITY 

In this section, we examine whether individual-agent se-curity composes in hierarchical multi-agent systems. We first present an empirical counterexample in which a prompt injec-tion hijacks system-level control flow despite every constituent agent being individually secured with CaMeL. We then show that individual CaMeL can nevertheless block certain attacks that require hijacking an individual agent’s control flow, us-ing the OMNI-Leak setup [22] as an example. Finally, we characterize theoretically when individual agent control-flow integrity composes to the system level.

B. Individually Secure Agents Defend Against Some Attacks 

Although individual-agent CFI does not compose in general, it can still prevent attacks that require hijacking the control flow of a particular agent. Consider OMNI-Leak [22], in which untrusted public data causes a SQL agent to access a private database. If the SQL agent satisfies CFI, this attack fails: the untrusted data cannot cause its PLLM to introduce the required private-database call. We verify this empirically using the OMNI-Leak orches-trator topology with each agent running CaMeL under the trivial security policy, and with GPT-5.2 as both PLLM and QLLM. We observe a prompt injection attack success rate of 0% (across 5 trials with temperature=1), while benign query accuracy is unchanged at 100%.

Under individual-agent CaMeL, a tool-derived value ( x) can be incorporated into the natural-language instruction passed to a child agent. Under Multi-CaMeL however, such a value is necessarily passed to the child agent via the variables argument, preventing the child’s PLLM from seeing its content. This separation is enforced by the Multi-CaMeL interpreter. 1) Instruction-channel integrity. The message argument of an agent-as-tool call must not depend on any tool output. This ensures that values derived from untrusted data cannot be exposed to the child agent’s PLLM as trusted natural-language instructions. 2) Cross-agent provenance preservation. When values are passed between agents via the variables argument, their associated capabilities and provenance are pre-served across the agent boundary. As we discuss in Section IV-C, the first property is suffi-cient to achieve system-level CFI. It prevents the boundary-laundering failure from Section III by ensuring that untrusted data cannot enter a downstream agent’s instruction channel. The second property allows multi-CaMeL to support non-trivial security policies globally: so long as provenance and capabilities are preserved across agent boundaries, a security policy S can be enforced globally by enforcing it at runtime for each individual agent, as CaMeL already does. Although our evaluations use the trivial security policy, we intentionally preserve the ability to use non-trivial security policies in multi-CaMeL. It is worth noting that, unlike with single-agent CaMeL, the multi-CaMeL interpreter is necessary for ensuring CFI independently of whether any security policies are configured. 

C. Security Guarantees 

Multi-CaMeL ensures that untrusted data cannot be incor-porated into the natural-language instructions seen by a child agent’s PLLM. Since each agent individually satisfies CFI, its possible control-flow plan is therefore fixed by trusted inputs. Starting from the root agent’s control-flow plan, the system recursively expands each agent-as-tool call site with the corresponding child agent’s control-flow plan. This yields a system-level control-flow plan determined only by the original user instruction and other trusted information. Untrusted data may still determine which branch of this pre-specified plan is taken. For example, a parent may call 

child_agent(query_1) if a tool returns a particular value and call child_agent(query_2) otherwise. Here, the tool result determines which child invocation occurs, but both possibil-ities were already specified by the system-level control-flow plan. Thus, untrusted data can steer execution among existing branches, but cannot introduce new control-flow paths. We refer to this as branch steering [27], rather than a CFI violation. Multi-CaMeL satisfies our notions of CFI and CaMeL-security. In Section VI, we discuss how multi-CaMeL fits into other notions of security guarantee, such as Termination-Insensitive Probabilistic Noninterference (TIPNI) of Garby et al. [28], and outline priorities for future work. V. U TILITY AND SECURITY EVALUATIONS 

We evaluate the utility tradeoff of multi-CaMeL against both 

individual-agent CaMeL (where each agent is individually running CaMeL but without additional restrictions on inter-agent communication) and no CaMeL (where agents are relying solely on model-side defenses rather than CaMeL). We measure utility on AssetOpsBench [20] and evaluate both security and utility on MultiAgentDojo, our multi-agent extension of the prompt-injection benchmark AgentDojo [12]. In both benchmarks, we find that prompt augmentation is necessary to achieve reasonable utility with individual CaMeL or multi-CaMeL. In particular, the default tool descriptions in AssetOpsBench and AgentDojo do not specify tool return schemas. This is largely unproblematic for non-CaMeL agents, which can infer the structure of a tool output after receiving it. In CaMeL, however, the PLLM must generate a program that parses the output before observing it, making the return schema necessary in advance. We therefore augment all tool descriptions with full return schemas, as was also necessary in the original single-agent CaMeL evaluations [1]. We view this documentation as a necessary component of the CaMeL and multi-CaMeL protocols rather than an inherent utility limitation: it is a modest, one-time augmentation that can be performed in advance for a given environment and tool set.

C. Failure Modes 

In this section, we qualitatively examine the failure modes observed in our experiments. For security, we focus on individual-agent CaMeL: it retains a small number of suc-cessful prompt-injection attacks, all of which exhibit boundary laundering, whereas we observe no successful attacks under multi-CaMeL. For utility, we analyze both individual-agent CaMeL and multi-CaMeL, since both exhibit benign task failures arising from the restrictions imposed by their pre-specified control-flow plans and, in the multi-CaMeL case, the additional constraints on cross-agent communication. 

1) Security Failures in Individual CaMeL: Every successful prompt-injection attack against individual-agent CaMeL was an instance of boundary laundering : untrusted data crossed an agent boundary and was incorporated into a downstream agent’s trusted natural-language instruction, thereby influenc-ing its control-flow plan. Multi-CaMeL prevents this failure mode by preserving the distinction between trusted instruc-tions and untrusted data across agent boundaries, and we observe no successful attacks against multi-CaMeL. User task 16 provides a concrete example. The user asks the system to provide Dora and Eve with feedback based on their websites, but one of the websites contains a prompt injection instructing the agent to send a malicious link to another user. Under individual-agent CaMeL, the Orchestrator embeds this injected content in the natural-language instruction passed to the Slack Agent, causing the Slack Agent’s PLLM to incorporate the injected action into its control-flow plan. Under multi-CaMeL, the website-derived content is instead passed through the sep-arate data channel and is never exposed to the Slack Agent’s PLLM as trusted instruction text. A non-CaMeL agent can respond by introducing a new tool or sub-agent invocation at runtime, whereas a CaMeL agent can only follow control-flow paths anticipated by its PLLM-generated program. We also observe failures caused by unchecked scope sub-stitution . In several AssetOpsBench trajectories, a sub-agent is unable to retrieve data for the exact asset, time range, or other scope requested and instead returns data for a nearby but different scope. Because the parent agent’s control-flow program is generated before receiving this response, it may proceed with the substituted data without recognizing that the original task constraints have been violated. VI. L IMITATIONS AND FURTHER WORK 

Our results establish that multi-CaMeL preserves control-flow integrity (CFI) in the hierarchical agent-as-tool setting considered in this work. This setting deliberately restricts both the topology of the multi-agent system and the secu-rity property we aim to guarantee. These restrictions leave several important questions open. We discuss two of these below: extending the approach to more general multi-agent architectures, and relating its guarantees to stronger notions of information-flow security. 

A. Beyond Trees 

We study hierarchical agent-as-tool systems in which the agent hierarchy forms a tree: each non-root agent has a unique parent, and all inter-agent communication occurs through parent-to-child calls and responses. This restriction simplifies the security model. For example, if an agent could have multiple parents, we would need to specify how concurrent invocations are handled and whether the child preserves state or conversational history across interactions, rather than being spawned fresh. Multi-CaMeL could, however, be extended from trees to directed acyclic graphs (DAGs), where the same agent may be invoked by multiple upstream agents. At a high level, the communication protocol can still be applied independently at each invocation boundary. When an agent is first invoked by a new parent, that parent could be treated as the trusted user for a fresh episode. Additional care would be needed if conversa-tional history were to be retained across invocations: previous interactions may contain outputs derived from untrusted data and therefore should not be incorporated into the context of a later invocation. Extending to even more general architectures introduces further challenges. Agents might communicate peer-to-peer rather than necessarily via a parent agent, they might com-municate asynchronously through message queues or a shared state, or they might participate in cyclic interactions in which information passes repeatedly between agents. In such systems there might be no single root agent, no unique direction of information flow, or no clear agent-as-tool boundaries at which to enforce the multi-CaMeL protocol. The central design principle of multi-CaMeL nevertheless suggests a pos-sible generalization: every communication mechanism that can influence another agent’s control flow should preserve the distinction between trusted instructions and data, and provenance should remain attached to data as it moves between agents. We therefore view multi-CaMeL as one instance of the broader multi-agent security principle that crossing an agent boundary must not implicitly upgrade the trust of information. Formally extending this principle to DAGs, cyclic graphs, shared-memory systems, and peer-to-peer agent architectures – as well as proving resulting system-level CFI and CaMeL-security – is an important direction for future work. 

B. Stronger Security Guarantees Than CFI 

In our work, we define control-flow integrity (CFI) and CaMeL-security (with respect to a security policy S), and show that multi-CaMeL (with security policy S) satisfies these properties. Concurrent work by Garby et al. [28] introduces LLMbda, a lambda calculus with information-flow guarantees for provenance-based defenses. They de-fine Termination-Insensitive Probabilistic Noninterference (TIPNI), an information-flow property requiring that observer-indistinguishable inputs induce compatible distributions over observer-visible outcomes, except for differences in termina-tion behaviour. In our setting, an agent or agent system would satisfy TIPNI if changes to untrusted inputs have no effect on the distribution of its actions and outputs, except through nontermination. Multi-CaMeL permits behaviors that would violate this condition: in particular, untrusted data may steer execution among branches of its control-flow plan, changing externally visible outputs, a phenomenon we refer to as branch steering. Such branch steering does not violate our definition of CFI. Thus, TIPNI rules out some behaviors permitted by CFI. Formally relating these guarantees would clarify their relative strength and scope. We leave this extension to future work. We consider two specific critiques of CaMeL raised in LLMbda and analyze their relevance to multi-CaMeL. 

1) The CaMeL Interpreter Misses Some Implicit Depen-dencies: Garby et al. observe that the CaMeL interpreter’s dependency tracking can miss implicit flows through control flow: a variable may remain labelled trusted even when its value depends on an untrusted condition, particularly through assignments on branches that are not taken. Multi-CaMeL inherits this implementation limitation because it extends the CaMeL interpreter. This does not affect the protocol-level argument of Section IV-C, which assumes that instruction-channel integrity is enforced, but it does mean that the current implementation may fail to enforce this property in cases involving implicit dependencies missed by the interpreter. Strengthening the CaMeL interpreter to soundly track such dependencies is therefore important future work. 

2) The CaMeL Retry Loop Leaks Information: Garby et al. identify CaMeL’s external retry loop as an information-leakage channel, since policy-dependent failures can reveal informa-tion across repeated retries. Multi-CaMeL, as implemented, does not retry failed executions and therefore does not inherit this specific issue. More broadly, however, information-flow guarantees rely on agents being suitably confined [30]. As agents become more strategic and communicate through in-creasingly complex channels, classical confinement techniques such as covert-channel enumeration and capacity reduction may be insufficient [31]. Establishing appropriate confinement guarantees for Multi-CaMeL remains an important direction for future work. VII. C ONCLUSION 

We show that securing each agent independently from indirect prompt injection is not in general sufficient to secure a multi-agent system: untrusted data can cross an agent bound-ary, be reinterpreted as trusted input, and thereby compromise system-level control-flow integrity. We call this failure mode boundary laundering, and demonstrate it empirically with a concrete control-flow hijacking attack. Multi-CaMeL offers control-flow integrity (and CaMeL-security if paired with security policies, S) at the system level for hierarchical agent-as-tool systems. We show ex-perimentally that multi-CaMeL improves on the security of individual-agent CaMeL, eliminating all instances of boundary laundering in MultiAgentDojo, our multi-agent extension of AgentDojo. Across our utility evaluations, the additional utility cost incurred by multi-CaMeL over individual-agent CaMeL is relatively small on average, but varies across models, with smaller costs for the strongest models evaluated. We also find that Multi-CaMeL’s utility cost relative to no CaMeL is smaller for more capable models. Our analysis is limited to the hierarchical agent-as-tool setting, and to the security guarantees captured by our notions of control-flow integrity and CaMeL security. Extending these ideas to DAG, cyclic, asynchronous, and peer-to-peer agent system topologies, and to stronger information-flow properties, remains open for future work. Nevertheless, the underlying principle we outline is broader than the particular architectures we study here: crossing an agent boundary should not implic-itly upgrade the trust status of information. As increasingly capable agents are composed into larger and more complex systems, preserving this distinction across their interfaces will be an important part of making security guarantees compose. APPENDIX BIMPOSSIBLE ASSET OPS BENCH TASKS 

A subset of AssetOpsBench tasks cannot be completed as literally specified because the required data does not exist in the benchmark environment (e.g., referenced data files that are absent, or sensors with no recorded observations in the requested period). To identify these tasks without relying on any single model’s claims, we pooled the trajectories from all evaluated configurations (five models, each run in vanilla, individual-CaMeL, and multi-CaMeL mode) and flagged a task as unsatisfiable if two conditions held. First, at least one trajectory had to contain tool-level evidence of data absence: a query with the correct asset, sensor, time period, or file scope whose raw tool output returned empty or not-found, as verified by an LLM judge instructed to assess data availability solely from tool outputs rather than from the agent’s own narration. Second, no trajectory in any configuration was permitted to contain a genuine completion of the task with real data; to enforce this, we discarded apparent completions whose final answers were in fact missing-data reports, zero-substitutions, or unsupported success claims (identified with a broad lexical filter over the final answers and manual spot-checks). This procedure flagged 29 of the 141 tasks: 216–223 (referenced data files absent from the environment), 430, 433, 434, 502, 506, 507, 508, 510, 511, 514, 515, 517, 518, 519 (Chiller 9, an asset with no recorded sensor history), 41, 42, 45 (power and supply-temperature sensors with no observations), and 10, 48, 420, 622 (individual tasks whose specific sensor, date range, or record set is empty). Because a task is retained whenever any trajectory contains a plausible real-data completion, this set is a conservative lower bound on the number of unsatisfiable tasks; we report results both on the full task set and with these 29 tasks excluded. The full list of tasks we removed from AssetOpsBench is as follows: 10, 41, 42, 45, 48, 216, 217, 218, 219, 220, 221, 222, 223, 420, 430, 433, 434, 502, 506, 507, 508, 510, 511, 514, 515, 517, 518, 519, 622.
