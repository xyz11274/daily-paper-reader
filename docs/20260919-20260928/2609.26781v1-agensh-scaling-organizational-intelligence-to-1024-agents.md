## 摘要
多智能体系统可以通过并发执行工作来降低复杂任务的延迟。已有若干开创性的harness框架支持多智能体系统。然而，当前多智能体harness的可扩展性往往受限于中心编排器分配任务和协调工作者的能力。为解决这一局限，我们提出了Agensh，一种无需中心编排器的可扩展自组织多智能体harness：并发工作者执行多智能体协作循环，以异步方式持续收集上下文、认领并自行分配子任务、采取行动并分享发现、验证结果以及合并进展。该循环由智能体组织基础设施支持，包含三个组件：共享工作区保存已提议、进行中和已完成的工作；消息接口让工作者进行通信；共享上下文保留可复用的发现和工作意图。为测试Agensh的可扩展性，我们在五个最难的ProgramBench任务上使用GPT-5.6-sol（high）对其进行评估。将智能体数量从1扩展到128，平均最终测试通过率从19.31%提升至28.78%，相对提升约49%。更大的组织更早达到相当的测试通过率。在pandoc上，将智能体数量从1扩展到1,024，最终测试通过率从33.89%提升至55.06%。工作者轨迹进一步表明，随着组织规模增长，不同形式的自组织协作逐渐涌现并标准化。这些结果揭示了智能体数量作为多智能体组织扩展通用智能前沿的新扩展维度，为在严格延迟约束或时间预算下的复杂任务提供了实用解决方案。

## Abstract
A multi-agent system can reduce latency on complex tasks by executing work concurrently. Several pioneering harness frameworks support multi-agent systems. However, the scalability of current multi-agent harnesses is often constrained by a central orchestrator's capacity to allocate tasks and coordinate workers. To address this limitation, we introduce Agensh, a scalable self-organized multi-agent harness without a central orchestrator: concurrent workers execute a multi-agent cooperation loop, continuously gathering context, claiming and self-assigning sub-tasks, taking action and sharing findings, verifying results, and merging progress in an asynchronous manner. The loop is supported by the agentic organization infrastructure comprising three components: a shared workspace holds proposed, ongoing, and completed work; a message interface lets workers communicate; and shared context retains reusable findings and work intentions. To test the scalability of Agensh, we evaluate it on the five hardest ProgramBench tasks with GPT-5.6-sol (high). Scaling from 1 to 128 agents raises the mean final test-pass rate from 19.31% to 28.78%, an approximately 49% relative improvement. Larger organizations reach comparable test-pass rates earlier. On pandoc, scaling from 1 to 1,024 agents raises the final test-pass rate from 33.89% to 55.06%. Worker trajectories further show that different forms of self-organized cooperation gradually emerges and standardizes as the organization grows. These results reveal the number of agents as a new scaling dimension for multi-agent organizations to expand the frontier of general intelligence, offering a practical solution for complex tasks under hard latency constraints or time budgets.

# Agensh 论文深度总结

## 1. 核心问题与整体含义

- **研究动机**：单智能体系统受限于单一上下文窗口、单一动作流和单一记忆流，在复杂长周期任务上延迟高、能力有上限。多智能体系统可通过并发执行降低延迟，但现有主流 harness 框架（Codex sub-agent、Claude Code sub-agent/agent teams、Copilot fleet、Kimi Agent Swarm）普遍采用 **orchestrator-worker（编排器-工作者）结构**，由中心编排器负责任务规划、分解、分配与结果整合。
- **核心瓶颈**：整体系统的可扩展性本质上受限于中心编排器的容量——它需要管理、协调大量工作者并整合其贡献，成为扩展的天花板。
- **整体含义**：论文提出 **Agensh**，一种**无中心编排器的自组织多智能体 harness**，将"智能体数量"确立为多智能体组织的新扩展维度，为硬延迟约束或时间预算下的复杂任务提供实用方案，并探索通过扩展协作规模来拓展通用智能前沿。

## 2. 方法论

### 核心思想
- 抛弃中心编排器，让并发工作者**异步、自组织**地执行统一的协作循环，通过轻量级"智能体组织基础设施"共享状态与进展。

### 多智能体协作循环（五步，每个工作者并发异步执行）
1. **收集上下文（Gather context）**：读取共享用户目标、当前状态、同伴进展与消息、累积发现，并与环境交互规划下一步。
2. **认领子任务（Claim sub-task）**：提出子任务并以 `CLAIM` 形式追加到共享上下文；若两个工作者的认领重叠或冲突，通过直接消息解决。
3. **采取行动（Take action）**：本地解决子任务，通过工具与环境交互；一旦建立可能帮助他人的发现，即写入共享上下文。
4. **验证结果（Verify results）**：将本地进展与子任务验收标准比对，不满足则迭代修正。
5. **合并进展（Merge progress）**：将贡献合并进共享工作区，并发布更新（变更内容、思路、验证证据）；若合并冲突，则纳入最新同伴进展、解决冲突后重新合并。

- 合并后回到第 1 步，基于新整合的工作与最新同伴更新开始下一轮。

### 智能体组织基础设施（三大组件）
- **共享工作区（Shared workspace）**：文件系统，保存进行中与已整合的工作，支持并发写、异步读、版本历史与合并冲突暴露。实现上使用 **Git 平台（Gitea）**，工作者在私有 checkout/分支上修改并整合到 main 分支。
- **消息接口（Message interface）**：共享任务频道承载团队公告，直接消息支持紧急一对一通信。低优先级频道消息在每轮循环开始时投递，高优先级直接消息在每次基础设施工具调用结束时投递；保留会话历史并异步投递。
- **共享上下文（Shared context）**：保留可复用发现与工作认领，思想源自 DeLM。工作者发布**类型化条目**：`OBSERVED`（观察到的行为）、`FACT`（确认的事实）、`FAIL`（被证伪的假设，价值最高）、`CLAIM`（正在进行的认领）、`PATCH_SUMMARY`（已完成变更，格式 `files= | idea= | evidence=`）。服务维护 append-only 数据库 + 近期记忆，并提供 **context grep 工具**支持搜索完整历史。

### 实现细节
- Agensh 是**叠加在单智能体 harness 之上的组织层**，而非替代：底层 harness 负责单个工作者的推理与行动，Agensh 负责组织级行为（身份、协作协议、事件路由、共享工作区访问、消息、共享上下文、恢复与存活机制）。
- 协作循环通过**每个工作者 prompt 中的工作流指令**实现，而非硬编码进运行时；除 worker ID 外所有工作者 prompt 完全相同，因此可插拔地连接不同底层 harness（如 Claude Code、Copilot）。
- 事件驱动运行时：Gitea 通过 server-sent event 触发通知拉取，Mattermost 通过长连接 + 重连补拉；事件去重、持久队列、失败重试、空闲检测（10 分钟无活动则提示继续）、无共享上下文条目则提醒发布。

## 3. 实验设计

- **Benchmark**：**ProgramBench**（智能体软件工程最具挑战性的基准之一），要求智能体在**无互联网访问**、**6 小时预算**下从零重建参考软件的行为。
- **任务选择**：选取 5 个最难任务（依据官方 extended 结果中 SOTA 模型的平均通过率）：
  - **FFmpeg**（多媒体处理，10,090 文件 / 1,549,005 行 / 75.51 MB）
  - **gromacs**（分子模拟，8,982 文件 / 815,539 行 / 47.30 MB）
  - **pandoc**（文档转换，2,767 文件 / 104,336 行 / 4.86 MB）
  - **PHP-src**（语言解释器，26,266 文件 / 2,812,757 行 / 119.76 MB）
  - **ctags**（代码索引，7,313 文件 / 246,228 行 / 9.15 MB）
- **对比维度**：以**智能体数量**为自变量（1、8、32、128，pandoc 上扩展到 1,024），固定模型与 harness。
- **评估指标**：最终测试通过率（canonical-kept pass rate）、达到给定通过率的时间（延迟）。
- **基线**：单智能体（1 agent）配置，并加 stop hook 与空闲检测以保证其充分利用 6 小时。

## 4. 资源与算力

- **模型**：GPT-5.6-sol（high reasoning effort），最大输入 token 272,000，最大输出 token 128,000。
- **底层 harness**：Copilot。
- **部署规模**：1,024 worker 实验分布在 **16 个节点，每节点 64 个智能体**。
- **时间预算**：统一 6 小时；采用错峰激活（第一小时每 30 秒启动一个，之后每 3 秒一个）；T−45 分钟与 T−5 分钟发送收尾提醒。
- **未明确说明**：论文**未披露具体 GPU 型号、GPU 数量、总算力消耗或训练时长**（该工作为推理/部署型实验，非模型训练），也未给出 token 消耗或成本估算。

## 5. 实验数量与充分性

- **实验组数**：核心为 5 个任务 × 4 个规模（1/8/32/128）= 20 组主实验，外加 pandoc 上 1,024 智能体的扩展实验；另含随时间变化的通过率曲线（前 2 小时）与轨迹分析。
- **充分性评价**：
  - **优点**：任务难度高、规模跨度大（1→1,024，跨越三个数量级），并同时报告最终分数与延迟两个维度，轨迹分析提供了定性证据。
  - **不足**：**未做消融实验**（如去掉共享上下文/消息接口/共享工作区各自的影响未量化）；**未与其他多智能体框架（orchestrator-worker 类）做直接对比**，仅与自身单智能体基线比较；任务仅 5 个（虽为最难），统计样本有限；**未报告方差/多次运行结果**，单次运行可能受随机性影响。
- **公平性**：模型、harness、worker 协议、评估配置在对比中保持一致，单智能体基线也加了 stop hook 与空闲检测以对齐 6 小时利用率，**控制变量较为严谨**；但缺乏跨框架对比使"无编排器优于有编排器"的结论证据不足。

## 6. 主要结论与发现

- **智能体数量是新扩展维度**：5 个最难任务上，1→128 智能体使平均最终通过率从 **19.31% → 28.78%**（+9.47 个百分点，相对提升约 **49%**）。
- **规模降低延迟**：更大组织更早达到相同通过率。pandoc 上 128 智能体在 30 分钟即超过 30% 通过率，32 与 8 智能体分别在 60、90 分钟达到，单智能体前 2 小时始终未达。
- **千级规模可行**：pandoc 上 1→1,024 智能体使通过率从 **33.89% → 55.06%**（1,024 比 128 的 50.94% 再高 4.12 个百分点，比单智能体高 21.17 个百分点）。
- **自组织协作随规模涌现并标准化**：
  - **8 智能体**：同伴协调实现（约定技术接口、独立实现；自主发现并解决认领重叠）。
  - **32 智能体**：跨多工作者的整合管理（同伴评审、反例导致撤回批准并修复、更广泛的同伴参与沟通）。
  - **128 智能体**：自组织专业化与工作流标准化（按经验选择评审者、责任转移、建立并复用标准化集成协议、修订协作协议）。
  - **1,024 智能体**：组织级角色专业化（多个集成者角色、联系多个候选集成者选首个有效响应者、同领域专家在他人失败后接管，增强鲁棒性）。
- 这些协作形式**完全自组织**：工作者自行选择协作者、划分责任、建立并修订工作流。

## 7. 优点

- **架构创新**：去除中心编排器瓶颈，用轻量级基础设施（共享工作区 + 消息接口 + 共享上下文）支撑自组织协作，设计简洁且可扩展至千级智能体。
- **可插拔性**：协作循环以 prompt 指令实现而非硬编码，可适配不同底层 harness（Claude Code、Copilot），工程实用性强。
- **共享上下文设计精巧**：类型化条目（尤其 `FAIL` 避免重复浪费预算）、append-only + context grep 支持长周期任务、mid-turn 投递机制保证信息及时性。
- **实验规模与跨度突出**：1→1,024 跨越三个数量级，同时报告质量（通过率）与速度（延迟）双重收益。
- **轨迹分析有洞察力**：定性揭示协作形式随规模演化的四阶段路径，为多智能体组织理论提供实证。
- **工程细节完备**：事件驱动运行时、去重、重试、空闲检测、错峰激活、收尾提醒等机制考虑周全。

## 8. 不足与局限

- **缺乏消融实验**：三大基础设施组件（共享工作区、消息接口、共享上下文）各自的贡献未被量化，无法判断哪一组件最关键。
- **缺乏跨框架对比**：未与 orchestrator-worker 类框架（如 Kimi Agent Swarm、Claude Code agent teams）在相同条件下直接比较，"无编排器更优"缺乏直接证据。
- **统计严谨性不足**：未报告多次运行的方差/置信区间，单次运行结果可能受随机性影响；任务仅 5 个，样本量小。
- **算力与成本未披露**：未说明 GPU 型号/数量、token 消耗、总成本，1,024 智能体的经济可行性难以评估。
- **应用限制**：依赖 Git（Gitea）与 Mattermost 等外部服务；任务限定为"从零重建软件"这一特定场景，向其他领域（如科研、开放域任务）的泛化性未验证。
- **评估偏差风险**：任务选择基于 SOTA 模型通过率（可能偏向某些模型擅长的领域）；无互联网约束下的重建任务与真实开发场景存在差异。
- **协作涌现的可靠性**：自组织协作虽展现优势，但冲突解决、认领重叠、协议标准化等依赖工作者自发行为，在更大规模或异构模型下是否稳定尚不明确。
- **潜在冲突与重复工作**：论文承认需要错峰激活以"减少范围争用"，暗示大规模下仍存在认领冲突与重复劳动开销。
