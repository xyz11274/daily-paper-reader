## 摘要
多智能体系统（MAS）越来越多地用于自动化企业工作流，这些工作流涉及多个专用智能体、外部工具以及长时间运行的任务执行。故障可能源于工具性能退化、上下文传播错误、协调中断，或反复的智能体交互导致任务无法完成。尽管现有的可观测性框架提供了追踪和日志，但诊断与修复大多在执行完成后进行，限制了运行时恢复的机会。我们提出了 ResonAct，一种运行时自愈框架，通过流式运行指标实现对多智能体系统的持续监控、诊断与修复。ResonAct 将执行追踪、智能体交互和工具调用摄入流式分析层，持续推导任务进度、上下文健康度和工具可靠性指标。这些指标作为运行时控制信号，用于检测异常执行模式，并利用结构化故障模型定位根因。基于诊断出的故障，ResonAct 动态选择修复策略并执行动作。该框架作为外部控制平面运行，能够在不修改应用智能体或编排逻辑的情况下进行干预。我们在企业工作流场景和 AppWorld 基准上评估了 ResonAct。结果表明，基于流式指标的分析能够识别执行退化并定位故障。此外，策略驱动的修复将任务完成率最多提高了 10.00 个百分点，在评估配置中，检测精确率范围为 70.59% 至 82.91%，召回率范围为 63.09% 至 100%，恢复率范围为 10.48% 至 46.67%，运行时开销范围为 $-0.25%$ 至 14.12%。

## Abstract
Multi-agent systems (MAS) are increasingly used to automate enterprise workflows involving multiple specialized agents, external tools, and long-running task execution. Failures may arise from tool degradation, context propagation errors, coordination breakdowns, or repeated agent interactions that prevent task completion. While existing observability frameworks provide traces and logs, diagnosis and remediation are largely performed after execution completes, limiting opportunities for recovery during runtime. We present ResonAct, a runtime self-healing framework that enables continuous monitoring, diagnosis, and remediation of multi-agent systems through streaming operational metrics. ResonAct ingests execution traces, agent interactions, and tool invocations into a streaming analytics layer that continuously derives task progress, context health, and tool reliability metrics. These metrics serve as runtime control signals for detecting anomalous execution patterns and localizing root causes using a structured failure model. Based on the diagnosed failure, ResonAct dynamically selects remediation policies and performs actions. The framework operates as an external control plane, enabling intervention without modifying application agents or orchestration logic. We evaluate ResonAct across enterprise workflow scenarios and AppWorld benchmarks. The results show that the streaming metric-based analysis identifies execution degradations and localizes faults. Furthermore, policy-driven remediation improves task completion rates by up to 10.00 percentage points, with detection precision ranging from 70.59% to 82.91%, recall from 63.09% to 100%, recovery rates from 10.48% to 46.67%, and runtime overhead ranging from $-0.25%$ to 14.12% across the evaluated configurations.

# ResonAct 论文深度总结

## 1. 核心问题与整体含义

- **研究动机**：LLM 驱动的多智能体系统（MAS）正被广泛用于企业工作流自动化（软件开发、工具编排、数据密集型任务），但自主性提升带来可靠性挑战。故障不仅来自传统软件缺陷，还源于智能体间交互、工具退化、上下文传播错误、协调中断、执行轨迹偏离等。
- **关键痛点**：现有可观测性框架（traces、logs、telemetry）主要提供"事后"可见性，故障检测与根因分析通常在执行失败或产生不良结果之后才进行。对于长时间运行的企业级智能体工作流，异常行为会带来大量不必要的计算开销（如递归行为、上下文膨胀、重复工具调用导致 token 消耗剧烈波动）。
- **核心主张**：需要一种**运行时（runtime）**的干预机制，在任务执行过程中持续监控、诊断并修复，而非事后补救。ResonAct 即为此提出——一个作为**外部控制平面**运行的运行时自愈框架，无需修改应用智能体或编排逻辑。

## 2. 方法论

### 核心思想
- ResonAct 构建一个**闭环控制回路**，包含六个阶段：(1) 运行时事件捕获 → (2) 流式指标构建 → (3) 故障检测 → (4) 稳定性过滤 → (5) 修复策略选择 → (6) 纠正性引导注入。
- 各组件通过事件流通信，独立于底层智能体框架，实现监控、故障分析与修复策略同应用智能体的**解耦**。

### 故障分类体系
将运行时状况组织为三类：
- **Common Failures**：瞬态错误、超时、重试失败；
- **Silent Failures**：上下文衰减、状态发散、冗余执行等无显式错误的退化；
- **Critical Failures**：协调崩溃、无界循环、级联失败。

### 关键技术细节
- **事件捕获**：通过可观测平台（Langfuse）生成事件，经 Kafka 流式转发；三类执行证据为智能体交互、工具调用、LLM 执行轨迹（spans、tokens、context）。
- **流式指标构建**：以执行上下文 $c$ 为作用域，增量计算指标状态 $M_c(t) = [m_1(c,t), \dots, m_K(c,t)]$。指标沿两个轴组织：
  - **分析单元**：query 级、agent 级、tool 级；
  - **计算机制**：计数型、嵌入型、LLM-as-judge 型。
- **故障检测**：每个故障检测器 $d_f$ 读取最新指标快照，输出二值判定 $d^{(k)}_{c,f} \in \{0,1\}$，构造候选故障信号 $F^{(k)}_{c,f} = (f, c, M^{(k)}_c)$。
- **稳定性过滤**：要求故障在连续 $r$ 个评估周期内被检出，$S^{(k)}_{c,f} = \prod_{\ell=0}^{r-1} d^{(k-\ell)}_{c,f}$，以抑制瞬态误报，$r$ 控制早干预与抗噪的权衡。
- **运行时反思与诊断**：由 LLM 对故障信号与执行证据进行反思，输出诊断摘要 $D^{(k)}_{c,f} = (q, e)$，其中 $q$ 刻画故障模式，$e$ 汇总证据（可能涉及的智能体、工具、路径）。强调这是**基于证据的解释**，而非确定性根因判定。
- **修复决策引擎**：输出 $A^{(k)}_{c,f} = (b, u, s, g, \rho_a)$，即是否干预、目标、策略、引导内容、是否授权重试。支持 LLM 策略与确定性规则策略，LLM 不可用时回退到确定性策略。
- **引导注入**：仅在 $b=1$ 时发布引导消息，在智能体下一次调用/重试边界注入其 prompt。**不修改进行中的 LLM 生成**。

### 关键指标（附录）
- Agent loop index：$L(c) = N_{repeated}(c)/N_{calls}(c)$；
- Average steps：$S(q) = N_{agent}(q) + N_{tool}(q)$，以经验 P95 为无界执行参考；
- Unnecessary path ratio：$U(q) = (N_{repeated\ agent} + N_{failed\ tool})/(N_{agent} + N_{tool})$；
- Delegation efficiency：$D(q) = N_{successful\ worker}/N_{delegated}$；
- Compactness、API call efficiency（短窗/长窗比值）、Tool/Agent health（失败率）、Tool-routing confidence（余弦相似度 + 温度 softmax）、LLM-judge scores、Agent activation accuracy。

## 6. 主要结论与发现

- **RQ1 检测**：跨工作负载与模型家族均可检出故障。Sales 上 Granite-8B 精确率 76.21%、召回 69.15%；Qwen3-8B 精确率 72.11%、召回 63.09%。AppWorld 召回达 100%（两模型），精确率 82.91%（Granite）/70.59%（Qwen），但 FPR 偏高（Granite 达 72.97%），暴露**灵敏度—选择性权衡**。
- **RQ2 修复**：所有四组配置完成率均提升，最高为 Sales + Qwen3-8B 从 73.67% → 83.67%（**+10.00 pp**）；Sales + Granite 从 80.83% → 88.00%（+7.17 pp）。AppWorld 增益较小（+5.13 pp / +4.76 pp），恢复率仅 32.06% / 10.48%，说明长而工具密集的轨迹更难修复。Sales 上 post-trigger retry 成功率高达 97.7%（43/44）。
- **RQ3 效率**：运行时开销从 $-0.25\%$ 到 $+14.12\%$。Sales 上 +5.66%（Granite）/ +2.04%（Qwen）；AppWorld Granite 几乎无变化（$-0.25\%$），Qwen 增加 14.12%。CPU 增幅约 4.18–4.84%，内存变化温和甚至下降（约 $-2.55\%$ 至 $-3.36\%$）。
- **总体洞察**：修复效果在结构化 Sales 工作流上更强；AppWorld 的异构长轨迹使修复与开销更不稳定。**高 post-trigger retry 成功率表明，当前瓶颈更多在于故障选择与校准，而非修复动作本身的执行**。
- **部署**：已作为技术预览集成到 IBM watsonx Orchestrate（WXO），当前为 detection-only 模式，通过 Confluent Kafka 流式处理，实现 agent-loop index 与 per-tool 失败率的增量计算。

## 7. 优点

- **架构解耦**：作为外部控制平面，无需修改应用智能体或编排逻辑，具备良好的框架无关性与可移植性。
- **无需训练**：基于可解释的流式指标规则，避免模型训练成本，且指标可跨检测器复用，修复策略可独立演进。
- **运行时闭环**：在智能体调用边界进行干预，实现真正的执行中自愈，而非事后分析。
- **指标设计系统化**：query/agent/tool 三级 × 计数/嵌入/LLM-judge 三类，覆盖进度、上下文健康、工具可靠性多维度，附录定义详尽、可复现。
- **稳定性过滤机制**：通过连续 $r$ 周期确认抑制瞬态误报，参数可调，设计合理。
- **工程落地验证**：结合 WXO 生产 issue 分析（904 个 issue）论证故障类别的运营相关性，增强实用说服力。
- **双模型双场景验证**：跨模型家族与工作负载，结论具备一定稳健性。

## 8. 不足与局限

- **缺乏消融实验**：稳定性参数 $r$、评估周期、各指标贡献、LLM 策略 vs. 确定性策略等关键设计选择未做系统消融，难以判断各组件必要性。
- **缺乏基线对比**：未与 LumiMAS、SentinelAgent、AgentOps 等现有 MAS 运行时监控方法直接对比，优势主张缺少横向证据。
- **误报率偏高**：AppWorld 上 FPR 高达 72.97%（Granite），意味着大量健康执行被干预，可能引入不必要的开销与路径扰动，检测器校准问题突出。
- **恢复率有限且不均衡**：AppWorld 恢复率低至 10.48%，长轨迹修复能力不足；恢复率与完成率提升的因果关系需更严格控制变量验证。
- **算力信息缺失**：未报告 GPU 型号、数量、推理时长，影响可复现性与成本评估。
- **诊断非确定性**：LLM 反思输出被明确定义为"基于证据的解释"而非确定性根因，诊断可靠性依赖 LLM 质量，存在偏差风险。
- **指标为启发式**：如 unnecessary path ratio、compactness、tool-routing confidence 等均被作者自认为启发式/非校准概率，可能误判合法重复调用。
- **样本与场景局限**：仅两个工作负载、两个 8B 模型，未覆盖更大模型、更多框架或真实生产流量；Sales 数据集为自建且刻意注入约 60% 故障场景，可能高估实际故障密度下的表现。
- **部署尚不完整**：WXO 集成仅为 detection-only 预览，修复效果的受控评估与用户验证仍属未来工作，实际生产收益尚未证实。
