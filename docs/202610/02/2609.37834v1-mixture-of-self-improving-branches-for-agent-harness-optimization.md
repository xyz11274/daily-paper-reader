## 摘要
框架优化为递归自我改进（RSI）提供了一个实用场景，其中智能体生成的修改通过执行反馈影响后续变更。近期如 Meta-Harness 等工作通过迭代代码生成与评估实现该过程，但保留了固定的开发集与提议策略。这些约束将演化限制在单一搜索轨迹上，增加了收敛到局部最优的风险。我们通过将搜索组织为具有演化开发子集与提议策略的分支，使改进过程本身具有自适应性。每个分支保留由其更多领先框架而非其他分支框架解决的开发案例，丢弃所有分支中每个领先框架都能解决的案例，并利用自身搜索历史修订其提议策略。为部署由此得到的互补框架，我们提出一个路由器，在执行前为每个新输入选择一个由开发集选出的分支头。在数学推理与智能体编码基准上，我们的系统相对于 Meta-Harness 取得了相对提升：奥林匹克级数学推理上 34.8%，Terminal-Bench 2.0 上 11.6%，SWE-bench Lite 上 3.8%，且框架选择与路由器配置仅基于开发数据。这些结果表明，演化分支目标与提议策略能够产生互补框架，路由器无需访问测试结果即可组合其优势。

## Abstract
Harness optimization provides a practical setting for recursive self-improvement (RSI), where agent-generated modifications inform subsequent changes through execution feedback. Recent work such as Meta-Harness implements this process through iterative code generation and evaluation, but retains a fixed development set and proposal policy. These constraints channel evolution along a single search trajectory, increasing the risk of converging to a local optimum. We make the improvement process itself adaptive by organizing search into branches with evolving development subsets and proposal policies. Each branch retains development cases solved by more of its leading harnesses than by those of other branches, drops cases solved by every leading harness across all branches, and revises its proposal policy using its own search history. To deploy the resulting complementary harnesses, we propose a router to select one development-selected branch head for each new input before execution. Across mathematical reasoning and agentic coding benchmarks, our system achieves relative improvements over Meta-Harness of 34.8% on Olympiad-level mathematical reasoning, 11.6% on Terminal-Bench 2.0, and 3.8% on SWE-bench Lite, with harness selection and router configuration based solely on development data. These results show that evolving branch objectives and proposal policies can yield complementary harnesses whose strengths a router combines without access to test outcomes.

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体的能力不仅取决于底层模型，还取决于其外围"框架"（harness）——包括检索、工具接口、控制流等。框架决定了模型接收什么信息、能采取什么行动、何时验证或修正工作。
- **递归自我改进（RSI）场景**：Meta-Harness 等工作通过迭代代码生成与评估实现框架自动化设计，智能体生成的修改通过执行反馈影响后续变更，构成一种实用的 RSI 形式。
- **核心问题**：Meta-Harness 等现有方法在整个搜索过程中保留**固定的开发集**和**固定的提议策略**，导致演化被限制在单一搜索轨迹上，容易收敛到局部最优。具体表现为：
  - 始终在同一批开发案例上评估候选框架，会忽视互补优势——某个框架可能解决了领先框架遗漏的案例，但总体排名较低，其能力得不到进一步发展机会。
  - 固定的提议指令无法根据搜索中涌现的优势和未解决的失败来调整探索优先级。
- **核心研究问题**：能否通过让每个分支的开发子集和提议指导自适应演化，来发现互补的框架并提升部署性能？

## 2. 方法论

### 核心思想
- 将框架搜索组织为**多个独立分支**，每个分支拥有自己的开发子集、候选历史与提议指导。
- 通过**比较各分支前沿覆盖度**动态调整开发案例归属，使分支目标随搜索演化。
- 每个分支利用**自身局部搜索历史**修订提议指导，形成差异化的探索优先级。
- 部署时使用**路由器**为每个新输入选择一个开发集选出的分支头（branch head），无需测试结果。

### 关键技术细节

**分支局部搜索与提议生成**
- 设 $H$ 为候选框架，$M$ 为动作语言模型，$P$ 为共享的编码提议器（Claude Opus 4.6）。
- 分支 $b$ 在迭代 $t$ 的目标为在其开发子集 $X_b^t$ 上的期望奖励：
  $$J_b^t(H) = \frac{1}{|X_b^t|}\sum_{x \in X_b^t} \mathbb{E}[r(f_M(H,x), x)]$$
- 每个分支的候选框架源代码、评估分数、执行轨迹存储于本地文件系统 $D_b^t$，提议指导存储于 `SKILL.md`。
- 所有分支初始时共享相同的种子框架、完整开发集 $X$ 和初始指导 $S_0$。

**开发驱动的轨迹演化**
- 定义分支前沿 $F_b^t$ 为按开发集平均奖励排名前 $q$ 的框架。
- 对每个开发案例 $x$，计算各分支前沿的覆盖投票：
  $$c_b^t(x) = \sum_{H \in F_b^t} \mathbb{1}[H \text{ 解决 } x]$$
- **移除规则**：若所有分支的所有前沿框架都能解决 $x$，则从所有子集中移除该案例（信号价值低）。
- **归属规则**：若某分支 $b$ 满足 $c_b^t(x) - \max_{b' \neq b} c_{b'}^t(x) \geq \Delta$（$\Delta$ 为归属边际），则该案例归 $b$ 所有，从其他分支移除。
- 否则子集成员保持不变。

**分支特定提议适应**
- 每个分支的指导 $S_b^t$ 由同一提议器 $P$ 根据当前指导与近期搜索记录更新。
- 更新指令要求提议器：在同一开发阶段内比较候选、区分重复证据与孤立成败、将局部成功与未解决失败转化为后续提议优先级。

**开发信息驱动的路由**
- 搜索结束后，每个分支选择在其最终开发子集上平均奖励最高的头 $\hat{H}_N^b$。
- 路由器 $R$ 使用动作模型 $M$、专家源代码、头独占开发案例（仅被一个头解决的案例）及两个头的输出构建。
- 使用 GEPA 优化路由指令，以头独占开发案例为训练数据。
- 每个新问题在执行前由路由器选择头，不使用专家输出或正确性反馈。

**完整流程（Algorithm 1）**
- 分支并行演化；当每个分支至少有 $q$ 个候选后开始剪枝；每 $C_p$ 次迭代比较前沿并更新开发子集；每 $C_s$ 次迭代修订指导。
- 当两者同时到期时，先更新开发子集再修订指导。
- $N$ 次迭代后，从最终分支头和开发证据构建路由器 $R$。

- **分支互补性**：各分支解决对方遗漏的案例，合并覆盖率比更强单个头高 4.0–9.0 个百分点（绝对值）。
- **路由器效果**：路由器在 Math-Gemini 上超过更强头 4.0%，在 TB2 上超过 1.7%，在另外两个设置上仅差一个测试案例。路由器恢复了两分支独占成功案例的 75.0%。
- **开发更新频率**：更频繁的更新（每迭代）显著优于每 3 或 5 迭代更新（62.0% vs 56.0% vs 53.0%）。
- **组件组合**：开发剪枝与提议适应同时启用效果最佳（62.0%），单独启用提议适应无提升（50.0%），单独启用剪枝为 54.0%，两者均无为 51.0%。
- **测试最佳分析**：本文的测试最佳框架在 3 个设置上超越 Meta-Harness 的测试最佳，在 Math-Sonnet 上持平。Math-Gemini 上路由器达到 62.0%，超过测试最佳单个框架的 58.0%。
- **机制发现**：分支演化出不同的框架机制，如 Branch 1 发展具体答案检查与证明义务路由，Branch 2 探索自由形式推导与双边闭合。

## 7. 优点
