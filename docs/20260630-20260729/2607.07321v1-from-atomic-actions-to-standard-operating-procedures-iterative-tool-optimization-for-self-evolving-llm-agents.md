## 摘要
工具利用使大语言模型（LLM）智能体能够与现实世界交互并解决复杂任务。然而，现有智能体框架主要依赖由细粒度原子操作（例如，基本的文件I/O或单轮搜索）组成的静态工具集，这迫使智能体为每个重复性工作流程重新发明底层逻辑，导致推理开销增加和失败率上升。在本研究中，我们提出智能体可以通过将这些原子操作合成为可重用的标准作业程序（SOP）来实现自我进化，这些SOP作为可调用的高阶工具，封装了多步逻辑。我们进一步引入了EvoSOP框架，该框架使智能体能够从执行轨迹中提取SOP，并通过构建、合并、评估和修剪的系统化生命周期迭代优化工具集。大量实验表明，与基线相比，EvoSOP显著提高了任务成功率，同时大幅减少了交互轮数。我们的分析还揭示，迭代工具优化促进了可靠且高效的工具使用模式，为开发自进化智能体提供了一条可扩展的路径。

## Abstract
Tool utilization enables Large Language Model (LLM) agents to interact with the real world and resolve complex tasks. However, existing agent frameworks predominantly rely on static toolsets composed of granular atomic actions (e.g., basic file I/O or single-turn search), which forces agents to reinvent low-level logic for every recurring workflow, leading to increased reasoning overhead and failure rates. In this study, we propose that agents can achieve self-evolution by synthesizing these atomic actions into reusable Standard Operating Procedures (SOPs), which function as callable higher-order tools that encapsulate multi-step logic. We further introduce EvoSOP, a framework that empowers agents to extract SOPs from execution trajectories and iteratively optimize the toolset through a systematic lifecycle of construction, merging, evaluation, and pruning. Extensive experiments demonstrate that EvoSOP significantly boosts task success rates while substantially reducing the number of interaction rounds compared to baselines. Our analysis also reveals that iterative tool optimization fosters reliable and efficient tool-use patterns, providing a scalable pathway for the development of self-evolving agents.

### 2. 论文提出的方法论

- **核心思想**：提出 **EvoSOP** 框架，通过一个**非参数的、迭代的“训练”流程**来优化代理的工具集。该流程模拟了机器学习中的前向传播、反向传播和正则化，实现代理的自我进化。
- **关键技术细节**：EvoSOP 包含四个协同工作的模块，形成一个完整的“工具优化生命周期”：
    1.  **构建器（Constructor）**：分析历史执行轨迹，识别出频繁、逻辑耦合的原子动作序列。将这些序列提取并重写为可调用的、包含轻量级逻辑（如错误处理）的 **SOP 代码**。
        - 形式化：`ξ'_i = fextract(ξ_i)`, `S_i = frewrite(ξ'_i, Fatomic)`
    2.  **合并器（Merger）**：检查新生成的 SOP 是否存在功能重叠。如果存在，则将它们合并为一个更通用、更强大的高阶 SOP，避免工具集膨胀。
        - 形式化：`S_b = ∪_{i∈b} S_i`, `S' = fmerge(S_b)`
    3.  **评估器（Evaluator）**：将新生成的 SOP 添加进工具集，让代理重新执行所有训练任务，收集执行轨迹和任务结果。这是对 SOP 实际效用的“实验验证”。
        - 形式化：`F' = Fatomic ∪ {fschema(s) | s ∈ S_b ∪ S'}`，并执行 `ξ_hat = gverify(F')`
    4.  **评审器（Reviewer）**：分析评估阶段的执行轨迹，对每个 SOP 的调用进行问责，分类为“最优执行”、“部分效用”、“负向干扰”等状态。最终**剪枝**掉那些高错误率、低效用或冗余的 SOP，确保工具集的精炼和可靠。
        - 形式化：`S_solid = {s | fcheck(s, R_s) ≠ remove, s ∈ S' ∪ S_b}`
- **算法流程**：采用**小批量**方式迭代。在每个迭代周期内，先由构建器从新批次轨迹中生成 SOP，合并器进行整合，然后评估器重新执行任务，最后评审器进行剪枝。并通过**检查点**机制选择性能最优的迭代结果作为最终模型。

### 8. 不足与局限

- **实验覆盖范围**：虽然实验在两个基准上进行，但场景数量相对有限。后续需要在更多、更复杂的真实世界任务（如机器人控制、软件工程）中进行验证。
- **依赖LLM的评判能力**：`Reviewer` 模块需要LLM来评判 SOP 的执行效果，其准确性依赖于底层LLM的分析和判断能力，可能存在偏差或误判的风险。
- **训练集依赖性**：工具集的构建依赖于初始的成功或失败轨迹。如果初始轨迹样本不足或不具有代表性，生成的 SOP 质量可能会受限。研究未深入探讨对训练数据质量的鲁棒性。
- **潜在的风险**：
    - **“象征性”反向传播的风险**：依赖LLM分析轨迹来抽象SOP，可能生成逻辑正确但实际执行有缺陷的代码（如案例中的“删除最新消息”错误），虽然评审器能部分解决，但仍无法完全避免。

- **应用限制**：框架假设环境是可以回退或重放状态（`gverify`），这在某些真实世界场景（如不可逆的物理操作）中可能无法直接应用。
