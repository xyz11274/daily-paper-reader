## 摘要
随着智能体从研究原型走向部署工具，其能力越来越依赖于模型外部的执行基础设施，通常被称为智能体执行框架。在固定模型权重的情况下变更该框架可大幅改变任务性能。当前智能体评估通常报告选定框架下的下游性能，而模型自主开发框架的能力却未得到充分探索。本文提出HarnessDev基准，它将评估单元从任务输出转向可运行基础设施。HarnessDev包含两个阶段：创建阶段中，智能体从最小种子和少量用例出发，构建完整的执行系统；演化阶段中，智能体从自身创建的框架起步，利用下游执行反馈迭代修订框架，目标是提升基准性能。随后我们从能力（留出基准集上的任务成功率）和效率（执行token成本）两个维度评估每个构建出的框架。本文报告的创建阶段结果涵盖6个创建大语言模型、4个领域、5个下游基准，共计2207个独立下游实例，开发过程中未接触预留的隐藏评估任务。我们发现，生成的框架在代码、搜索与研究领域仍远落后于成熟的人工设计参考框架，而在写作和机器学习实验领域则能够匹配甚至超越选定的参考框架，且执行成本差异较大。演化带来了一定性能提升，但提升不稳定，仅能部分迁移到未见过的任务上。基于固定运行时模型的实验进一步表明，性能提升高度依赖于执行框架的模型，说明跨模型迁移能力有限。

## Abstract
As agents move from research prototypes to deployed tools, their capability increasingly depends on model-external execution infrastructure, commonly termed the agent harness. Changing this harness while holding model weights fixed can substantially alter task performance. Current agent evaluations typically report downstream performance under a chosen harness, leaving a model's ability to develop the harness itself comparatively underexplored. We introduce HarnessDev, a benchmark that shifts the unit of evaluation from task outputs to runnable infrastructure. HarnessDev covers two stages. In Creation, the agent starts from a minimal seed and a small number of cases, then builds a complete execution system. In Evolution, it starts from its own created harness and iteratively revises it using downstream execution feedback, with the goal of improving benchmark performance. We then evaluate each constructed harness on capability (task success on held-out benchmarks) and efficiency (execution-token cost). The reported Creation results cover six creator LLMs, four domains, and five downstream benchmarks totaling 2,207 unique downstream instances, with hidden evaluation tasks withheld from development. We find that generated harnesses remain substantially behind mature human-engineered references on code and on search and research, while matching or exceeding the selected references on writing and machine-learning experimentation, with large variation in execution cost. Evolution produces some performance gains, but they are unstable and transfer only partially to held-out tasks. Experiments with a fixed runtime model further show that the gains depend strongly on the model executing the harness, indicating limited transfer across models.

- 当前主流的智能体评估方案，都是预先选定一个固定harness，仅评估模型在该harness下的下游任务性能，完全将harness作为评估的固定配置，而非大模型需要自主开发迭代的对象。
- 因此，大语言模型是否能够自主创建、迭代优化自身的执行harness这一关键问题，尚未得到系统探索和评估，这就是本文要解决的核心问题。

# 2. 提出的方法论
## 核心思想
将智能体评估的对象从「单任务输出」转向「可持久运行、可迭代的执行基础设施」，系统评估大模型从零构建harness、以及基于反馈迭代优化harness的能力。

## 关键技术细节
- 整体分为两个评估阶段：
  1. **Creation（创建阶段）**：给大模型提供一个最小可用的弱种子harness（仅保留基础输入输出接口，无任务执行逻辑、无循环规划验证模块等），加上少量开发用例，要求大模型从零构建出完整可用的目标领域harness。
  2. **Evolution（演化阶段）**：大模型基于自身在Creation阶段得到的初始harness，利用下游执行得到的反馈，迭代修订优化harness，目标是提升下游任务性能。
- 评估设计上，将**创建harness的Creator LLM**和**运行harness执行下游任务的Executor LLM**分离，便于单独评估harness本身的质量，同时支持两种评估模式：
  - Self-Eval：Creator同时作为Executor，评估模型自建harness对自身能力的适配效果
  - Unified-Eval：所有不同Creator生成的harness都用同一个固定Executor运行，消除Executor差异，直接比较不同harness的质量
- 评估从两个维度展开：
  - 能力维度：生成的harness在预留的隐藏测试集上的下游任务成功率
  - 效率维度：生成的harness运行时消耗的Executor token成本

- **覆盖场景与基准**：
  - Creation阶段覆盖4个领域，共5个下游基准，总计2207个独立下游测试实例：

- **对比对象**：每个生成的harness都会和弱种子harness、成熟的人类工程化设计的harness参考结果做对比，评估大模型自建harness和人工方案的差距。
- 实验对象：评估了6个当前前沿的Creator LLM：Opus 4.8、GPT-5.5、Gemini 3.1 Pro、DeepSeek V4 Pro、Qwen 3.7 Max、Seed 2.0 Pro。

# 6. 主要结论与发现
- **Creation阶段结果**：
  大模型生成的harness性能差异显著，在代码、搜索研究领域，生成的harness性能远落后于成熟的人工设计harness；在写作、机器学习实验领域，生成的harness性能可以匹配甚至超越所选的人工参考harness；同时不同模型生成的harness执行token成本差异很大，且更高的成本不代表更好的性能；生成的harness大多存在对原Creator模型的适配性，更换Executor模型后性能会明显下降，跨模型迁移能力有限。
- **Evolution阶段结果**：
  大模型可以利用下游反馈对初始harness做一定改进，但性能提升不稳定，开发阶段得到的提升在预留的隐藏测试集上会大幅缩水，只有部分增益能够保留；仅当Creator和Executor为同一模型时，能得到稳定的hold-out增益，固定Executor的情况下多数模型演化后反而出现性能下降，说明演化增益高度依赖运行时模型，跨模型迁移性差；优化过程中容易过拟合到开发反馈集，最终选定的版本很少是held-out性能最优的版本。

# 7. 方法与实验设计的亮点
- 首次提出了系统评估大语言模型自主构建、演化自身执行harness能力的基准，填补了该领域的评估空白，将智能体评估从「任务解决能力」拓展到「系统构建维护能力」，符合当前智能体落地的实际需求；
- 评估设计严谨，分离了Creator和Executor角色，区分了Self-Eval和Unified-Eval两种场景，能够分别评估harness对原模型的适配性和跨模型通用性；
- 严格区分了开发集和预留隐藏测试集，所有生成的harness都做了合规性审计，避免了违规作弊得分，保证了评估结果的可信度；
- 同时从能力和效率两个维度评估harness质量，揭示了高成本不代表高性能的现象，更符合实际部署需求。

# 8. 不足与局限
- 目前Evolution阶段仅覆盖代码领域，未拓展到Creation阶段的其他领域，覆盖范围有限；
- 人类基线结果不均匀，无法保证所有基线都是最优方案；
- Evolution每个Creator-Runtime设置只得到一条演化轨迹，且held-out评估仅覆盖SWE-Pro，无法支持不确定性估计和更宏观的统计结论；
- 开发环境在整个过程中保持固定，没有探索演化得到的harness能否自身作为新的开发环境支持进一步演化；
- Unified-Eval虽然固定了Executor，但无法完全消除harness和Executor之间复杂交互带来的差异，无法完全隔离模型差异。
