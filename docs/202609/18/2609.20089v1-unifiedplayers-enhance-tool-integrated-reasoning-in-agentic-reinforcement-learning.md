## 摘要
自演化方法通过允许使用工具的智能体生成自己的训练数据，减少了对人工标注轨迹的需求。然而，现有方法通常将轨迹生成与评估分离，依赖于无法适应新出现失败模式的静态验证器，或依赖于可能强化跨轨迹共享错误的自洽性信号。联合调整规划、执行和评估提供了一种有前景的替代方案，但也引入了一个根本性的协调挑战：每个组件都会不断改变用于训练其他组件的数据或反馈。我们用 UnifiedPlayers 应对这一挑战，这是一个协作框架，包含生成任务的规划玩家、通过 Python 工具调用生成多轮轨迹的执行玩家，以及构建可执行验证器的评估玩家。我们设计了角色特定的奖励，在 GRPO 下协调三个玩家朝向共享学习目标。在两个模型骨干和十二个推理基准上，UnifiedPlayers 在数学推理上至少比最强先前基线高出 3.5%，在通用推理任务上高出 3.9%。此外，学习到的验证器达到 84.2% 的对抗检测准确率，同时其奖励信号的每题方差是自洽性基线的 2.03 倍，从而提供更具区分度的验证。这些结果凸显了专用玩家之间的合作是通往自增强工具集成智能体的一条有前景的路径。

## Abstract
Self-evolving methods reduce the need for human-annotated trajectories by allowing tool-using agents to generate their own training data. Yet existing methods typically separate trajectory generation from evaluation, relying on static verifiers that cannot adapt to emerging failure modes or self-consistency signals that may reinforce errors shared across trajectories. Jointly adapting planning, execution, and evaluation offers a promising alternative, but introduces a fundamental coordination challenge: each component continuously changes the data or feedback used to train the others. We address this challenge with \textbf{UnifiedPlayers}, a cooperative framework comprising a Planning Player that generates tasks, an Execution Player that produces multi-turn trajectories with Python tool calls, and an Evaluation Player that constructs executable verifiers. We design role-specific rewards that coordinate the three players toward a shared learning objective under GRPO. Across two model backbones and twelve reasoning benchmarks, UnifiedPlayers outperforms the strongest prior baseline by at least 3.5\% on mathematical reasoning and 3.9\% on general reasoning tasks. Moreover, the learned verifier achieves 84.2\% adversarial detection accuracy, while its reward signal exhibits 2.03$\times$ higher per-question variance than a self-consistency baseline, providing more discriminative verifications. These results highlight cooperation among specialized players as a promising path toward self-enhanced tool-integrated agents.

## 1. 论文的核心问题与整体含义

- **研究动机**：训练工具使用型 LLM 智能体需要大量多轮工具调用轨迹，但人工标注成本高；自演化方法让智能体自行生成训练数据，可减少人工依赖。
- **核心问题**：现有自演化方法通常将“轨迹生成”和“评估”分离，依赖静态验证器或自一致性信号。静态验证器难以适应新失败模式；自一致性可能强化多条轨迹共享的错误，导致错误伪标签和误导性优势更新。
- **关键挑战：循环相互依赖（cyclic interdependence）**：若规划、执行、评估三者同时自适应，则：
  - 规划改变任务分布；
  - 执行改变轨迹和失败模式；
  - 评估改变奖励信号；
  - 三者互相改变对方的学习环境。
- **可能退化**：规划偏向简单、重复、不可验证任务；执行强化被评估器错误接受的轨迹；评估退化为“全接受”“全拒绝”或重复模板。
- **整体含义**：论文提出 **UnifiedPlayers**，将规划、执行、评估建模为三个专业化玩家，通过共享可执行证据协作，而不是共享单一标量奖励或共享参数。目标是在智能体强化学习中增强工具集成推理，实现自增强工具智能体。

## 2. 方法论：核心思想、技术细节与算法流程

### 2.1 三个玩家

- **Planning Player / Task-Setter**：生成多步、可验证的数学任务。
- **Execution Player / Solver**：对任务生成多轮轨迹，交错自然语言推理与 Python 工具调用。
- **Evaluation Player / Critic-Coder**：为任务生成可执行 Python 验证器，判断轨迹是否正确，并定位最早失败步骤。

### 2.2 共享可执行证据

- 对每个任务：
  - Planning 生成任务 \(q\)；
  - Execution 采样 \(K=8\) 条原始轨迹；
  - Evaluation 生成 \(M=4\) 个候选验证器；
  - 固定扰动引擎对每条轨迹生成 \(P=5\) 个对抗变体。
- 验证器经解析、编译后，在 Python 沙箱中同时作用于原始轨迹和扰动轨迹。
- 结果形成 **共享裁决矩阵**：
  - 行：有效验证器；
  - 列：原始轨迹与扰动轨迹；
  - 元素：接受/拒绝。
- 该矩阵是三个玩家奖励的共同证据来源，但每个玩家只使用不同摘要。

### 2.3 角色特定奖励

- **Planning 奖励**：
  - 鼓励任务处于 Execution 能力边界附近；
  - 鼓励可写出有判别力的验证器；
  - 惩罚重复问题。
  - 不确定性 \(U(q)=\min(\hat p,1-\hat p)\)，其中 \(\hat p\) 是多数答案比例。
  - 验证器可写性 \(V(q)\) 与有效验证器比例、对抗拒绝率有关；若无有效验证器或无扰动拒绝，则 \(V(q)=0\)。
- **Execution 奖励**：
  - 等于有效验证器对轨迹的平均接受率；
  - 用可执行检查替代多数投票伪标签，因此执行样本间一致并不保证高奖励。
- **Evaluation 奖励**：
  - 原始轨迹接受率；
  - 对抗扰动拒绝率；
  - 验证器代码冗余惩罚。
  - 全接受验证器无对抗奖励，全拒绝验证器无原始接受奖励，重复模板受冗余惩罚。

### 2.4 交替 GRPO 优化

- 每个外层迭代依次更新：Planning → Execution → Evaluation。
- 更新某个玩家时，另外两个玩家固定。
- 使用 GRPO：对同一上下文下采样的候选组进行组内奖励归一化，得到优势。
- 目标包含裁剪重要性比与 KL 惩罚；参考策略为每个外层迭代开始时的检查点。
- 设计上不共享参数、不组合奖励、不跨玩家传播梯度。
- 后续块使用同一迭代中已更新的前序玩家检查点，从而获得“新鲜反馈”。
- 理论分析指出：块内记录固定时优化局部稳定，但不保证单调改进或全局收敛。

## 3. 实验设计

### 3.1 模型与训练设置

- **两个骨干模型**：
  - Qwen3-4B-Base；
  - MiMo-7B-Base。
- 三个玩家均从同一骨干初始化。
- 基于 VeRL 实现，使用 VeRL-Tool 沙箱执行 Python。
- 沙箱限制：仅标准库、每次调用 10 秒超时、512 MB 内存上限。
- 每个任务执行 \(K \cdot M \cdot (1+P)=8 \times 4 \times 6=192\) 次沙箱执行。
- 每个外层迭代三个 GRPO 更新块；共三个外层迭代。

### 3.2 Benchmark

- **7 个数学推理基准**：
  - AMC、MATH-500、GSM8K、Minerva、Olympiad-Bench、AIME24、AIME25。
  - AMC 和 AIME 因题量小使用 mean@32，其余多为 greedy pass@1。
- **5 个通用推理基准**：
  - SuperGPQA、MMLU-Pro、BBEH、GPQA-D、HumanEval。
  - HumanEval 属于代码任务，但被列入通用域平均。
- 合计 **12 个基准**。

### 3.3 对比方法

- **Vanilla**：原始骨干，无工具、无后训练。
- **Tool-augmented**：同一骨干，推理时可使用 Python 工具，但无 RL 训练。
- **Absolute Zero**：自生成代码推理任务。
- **R-Zero**：Challenger 与 Solver 交替训练，Solver 使用多数投票伪标签。
- **Socratic-Zero**：Teacher 评估和精炼问题，Solver 学习反馈。
- **Agent0**：最接近的前作，交替训练 Curriculum 和 Executor；Curriculum 奖励依赖执行者自一致性与工具调用频率，Executor 使用多数投票伪标签。
