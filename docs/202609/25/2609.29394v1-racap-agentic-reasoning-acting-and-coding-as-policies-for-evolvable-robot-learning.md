## 摘要
通用机器人智能体必须从经验中学习、迁移到新任务并高效行动。代码即策略（Code as Policies, CaP）方法在运行时生成和修复程序，会带来延迟，并将可复用机制与任务特定决策纠缠在一起。我们提出 RACaP，一个智能体框架，将编码移至演化阶段，并在部署时使用推理-行动（Reasoning-and-Acting, ReAct）循环调用冻结的、类型化的策略 API。两阶段策略将能力课程学习与自主自演化相结合，以改进 API、ReAct 执行框架和经验记忆。这些 API 编码可复用的物理机制，同时暴露参数以供运行时自适应。ReAct 结合任务特定的工作记忆、长期经验记忆和视觉反馈，以选择动作、验证结果并从失败中恢复，而无需修改源代码。RACaP 在 LIBERO-90 上达到 54.4% 的成功率，在零样本 LIBERO-PRO 上达到 45.0%，在 LIBERO-Long 上达到 46.0%，而 CaP 基线在长时程任务上最高仅为 4.0%。在 LIBERO-PRO 上，其成功率是 CaP 基线的 2.5 倍，策略时间中位数加速 1.9 倍。为实现高效的机器人端部署，采用拒绝采样微调将 GPT-5.6 的 ReAct 决策蒸馏到 Qwen3-VL-8B-Instruct 中，实现每次决策推理加速 13.2 倍，并将重复物理调用从 16 次减少到 4 次。这些结果表明，将可复用代码与运行时决策分离，有助于持续演化、有效迁移和高效的长时程控制。

## Abstract
General-purpose robot agents must learn from experience, transfer to new tasks, and act efficiently. Code as Policies (CaP) methods generate and repair programs at runtime, incurring latency and entangling reusable mechanisms with task-specific decisions. We introduce RACaP, an agentic framework that moves coding to evolution and uses a Reasoning-and-Acting (ReAct) loop to call frozen, typed Policy APIs at deployment. A two-phase strategy combines capability curriculum learning with autonomous self-evolution to improve the APIs, the ReAct harness, and experience memory. The APIs encode reusable physical mechanisms while exposing arguments for runtime adaptation. ReAct combines task-specific working memory, long-term experience memory, and visual feedback to select actions, verify outcomes, and recover from failures without modifying source code. RACaP achieves 54.4% success on LIBERO-90, 45.0% on zero-shot LIBERO-PRO, and 46.0% on LIBERO-Long, compared with at most 4.0% for CaP baselines on long-horizon tasks. On LIBERO-PRO, it achieves 2.5 times the success rate of CaP baselines and a 1.9-fold speedup in median policy time. For efficient on-robot deployment, rejection-sampled fine-tuning distills GPT-5.6 ReAct decisions into Qwen3-VL-8B-Instruct, yielding a 13.2-fold per-decision inference speedup and reducing repeated physical calls from 16 to 4. These results show that separating reusable code from runtime decisions supports continued evolution, effective transfer, and efficient long-horizon control.

## 1. 核心问题与研究动机

- **背景**：通用机器人智能体需要（i）从经验中学习、（ii）把学到的知识迁移到新任务、（iii）在物理执行时保持高效与可响应。语言/视觉语言模型可以把开放指令转成语义计划，但底层"可调用技能"通常是固定的。
- **Code as Policies（CaP）的困境**：CaP 在任务到达后**运行时生成与修复机器人程序**，灵活但代价高——CaP-X 一次代码迭代需 6.8–23.8 秒，多轮试错需 60.8–113.6 秒；且生成的程序常把**可复用物理机制**（抓取高度、接触几何）与**任务特定常量/决策**（物体名、坐标、偏移）混在一起，换任务就得重写。
- **已有自改进 CaP 的不足**：
  - RATS 用"新颖性/可学习性"的 play 目标收集代码，但该目标不保证对下游任务有益。文中对照实验显示：在 LIBERO-90 上 play 反而把成功率从 21.1% 降到 11.1%，零样本 LIBERO-PRO 从 17.8% 降到 8.3%。
  - ASPIRE 验证并检索程序修复，但很多修复仍绑定失败观测中的固定距离/抓取高度；两者仍在执行期保留源码生成或修复。
- **核心研究问题（evolution-to-execution problem）**：CaP 系统应如何在**演化期代码**与**运行时决策**之间划分边界，从而既能持续演化、跨任务迁移，又能适应当前物理状态？
- **论文主张**：把**编码移到演化阶段**，运行时只保留 ReAct 循环中的**可操纵函数调用**。代码存"跨任务提升成功率的物理机制"，ReAct 存"场景相关选择"（动作顺序、参数、恢复、停止）。二者接口需同时具备**可靠性**与**灵活性**。

## 2. 方法论

### 2.1 核心思想
- 系统 Π = (A_θ, π_φ, M)：A_θ 为带类型 Policy API 库（实现参数 θ），π_φ 为运行时 ReAct 策略（框架参数 φ），M 为长期经验记忆。
- **部署期冻结源码**：π_φ 可改变工具或参数，但**不能编辑源代码**；所有物理操作都返回控制权给 ReAct。
- **演化期产出三件持久制品**：Policy APIs + ReAct harness + 经验记忆。

### 2.2 形式化目标
- 原生成功 S(τ, A_θ, π_φ, M) ∈ {0,1}，ReAct 轮数 T(τ, A_θ, π_φ, M)，开发集 D_dev。
- **API 选择（式2）**：在固定 π_φ、M 下，选候选 θ′ 使在**同一批任务、同一 seed、同一预算**下的**配对净增益**最大：
  θ* = argmax_θ′ Σ_{τ∈D_dev} [S(τ, A_θ′, π_φ, M) − S(τ, A_θ, π_φ, M)]
  → 保留"配对增益 > 配对回退"的机制，从而奖励跨任务泛化性。
- **harness/记忆选择（式3）**：固定 API 后按**字典序**目标选 (φ*, M*)：先最大化总成功，成功并列时才最小化总轮数 → 防止"更快但更差"的智能体胜出。
- **可操纵性（steerability）**：通过暴露带类型的参数（grasp、clearance、yaw、contact mode 等）保留随指令/场景变化的自由度。

### 2.3 Phase 1：能力课程学习
- 动机：从零开始的自主演化中，一次失败会混合感知、抓取、放置、路由、停止等多重错误，无法归因，易陷入局部最优。
- 课程分 S0–S6 七个阶段、四个能力层级：
  - **Execution**：Seed（基础 pickplace）+ Geometry（几何）。
  - **Recovery**：ReAct（重试）、Reports（失败反馈）、Visual（视觉校正）→ 41 任务 transport cohort 从 13/41（31.7%）升到 28/41（68.3%）。
  - **Breadth**：Six APIs（六种接触力学 API）+ API fixes（稳定化）。
  - **Orchestration**：Harness（工具路由、记忆、效率）→ 全 90 任务从 40/90（44.4%）升到 48/90（53.3%）。
- 编码智能体**不使用特权信息**（如物体坐标），只从指令、rollout 视频、工具轨迹与成功信号学习。

### 2.4 Phase 2：自主自演化
- harness 聚类当前失败、按共同成因分组，分析视觉 critic 对物体/夹爪/目标的运动摘要，让编码智能体提出**单一变更**（API、参数暴露、工具报告、ReAct 路由、记忆）。
- 提案须带预测增益、回退风险与明确拒绝条件；经语法编译与基础测试后进入仿真验证；**仅在配对原生成功严格提升时替换 parent**，平局与回退归档。
- 规模：596 个开发 episode、32 个提案、23 个候选验证、9 次成功晋升（覆盖 transport T1–T4、stacking、articulation、紧凑控制、路由、效率）。

### 2.5 运行时结构（冻结后）
- **六种 Policy API**：`pickplace`、`insert`、`stack`、`push`、`articulate`、`actuate_control`，接收 grasp type/clearance/target 解释/yaw/contact mode 等参数，返回可读状态、测量值与新图像。
- **双层 ReAct**：
  - *Full ReAct*：解析完整指令、排序因果目标、检查语义状态、跨六 API 路由（含 `task_plan`、`task_plan_review`、`state_preflight`、`state_decide` 四个带类型角色）。
  - *Transport ReAct*：子控制器，专注单源–目标子目标（`transport_decide`、`transport_reflect`，用前后图像做视觉诊断）。
- **双结构记忆**：工作记忆（当前 episode、随公观测与工具报告更新，每 episode 重置）+ 长期经验记忆（可复用的动作前提、恢复经验、API 能力边界，不含任务答案/绝对坐标/评估器状态）。
- 每个执行轮输出 schema 校验的调用记录（参数、报告、模型身份、延迟、token、成本）；**评估期绝不生成、编译或修复 Python 代码**；原生奖励/评估器状态不进入部署观测。

### 2.6 拒绝采样微调（RFT）加速 ReAct
- 将 GPT-5.6-sol 教师的 ReAct 决策蒸馏进本地 Qwen3-VL-8B-Instruct。
- 数据原则：仅保留**原生成功 + schema 可执行 + 视觉证据有效**的教师 rollout，得到 54 条接受 / 40 条拒绝决策。
- 训练角色专属 LoRA adapter，**冻结基座模型与视觉编码器**，loss 仅施加于教师响应 token。

## 6. 主要结论与发现

- **演化有效**：Phase 1 建立可执行、可诊断的基本能力（演化时 48/90 = 53.3%，评估回放 42/90 = 46.7%）；Phase 2 归档制品达 49/90 = **54.4%**。

- **长时程靠组合而非缩短轨迹**：LIBERO-Long Phase 2 = 23/50 = **46.0%**，Phase 1 = 32.0%，代码生成基线仅 2.0%–4.0%；增益集中在 On（40%→65%）与 Turnon（20%→50%），平均 ReAct 轮数反而从 8.22 升到 8.72。
- **持久代码需严格类型接口**：RATS-90 从 17.8% 跌到 8.3%、调用数升到 45.2、耗时 954 s，根因是 helper 函数与新生成调用脚本之间的接口漂移。
- **具备一定测试时适应能力**：每任务族一次校准 trial 使 Phase 1 +8.3 pp、Phase 2 +10.0 pp；代码生成基线响应混乱甚至为负（CaP-X −3.3 pp、RATS-90 −8.4 pp）。
- **跨具身需目标域演化**：冻结 Phase 2 在 Robosuite 仅 17.1%（低于 CaP-X 25.7%）；经域内演化后 RACaP-RS 达 31.4%，与 RATS-RS 持平但仅需 32.9 s / $0.089（对比 90.7 s / $0.159）。
- **蒸馏可行**：RFT 将教师决策精确一致率从 83.3% 提到 **97.6%**，可执行动作一致率

**（接上文）**可执行动作一致率亦明显提升，说明教师级 ReAct 决策可被本地 8B 模型有效承接；作者明确将 RFT 定位为**延迟/成本优化手段**，而非原生成功率的提升来源。

- **接口类型化是"演化—执行"边界成立的关键条件**：RATS-90 的失败审计（181/321 次失败源于 caller 与 saved function 之间的 key/dtype/参数不匹配）与 RACaP 六 API 的类型化设计形成直接对照，说明持久化代码若无严格 schema 约束，反而会成为迁移负担。
- **总体叙事**：RACaP 用"演化期改码、执行期只调函数"的划分，把 CaP 的**运行时试错成本**转化为**离线一次性的能力积累**，从而在零样本迁移与长时程任务上同时取得相对代码生成基线的显著优势。

## 7. 局限性与未来工作

- **仿真-only，无真机验证**：全部结论来自 LIBERO / Robosuite 系列仿真环境，未涉及真实机械臂的感知噪声、标定误差、接触动力学不确定性。跨具身实验虽改变硬件与控制后端，但仍在 Robosuite 框架内，**不能等同于真机泛化**。
- **in-domain 增益偏小且统计力不足**：Phase 2 在 LIBERO-90 上仅 +1 任务（48→49），且仅 seed 0 单次评估；LIBERO-Long 的配对检验 p = 0.118 未达显著。核心论点的支撑主要落在**零样本迁移**指标上，而非同分布性能。
- **模型版本不一致引入混淆**：演化用 GPT-5.6-sol、评估统一用 GPT-5.5，作者自认这是图 2(a) 与图 4(a) 差异的来源。这意味着 Phase 1/Phase 2 与基线之间的差距**不能完全归因于方法本身**，也包含演化—评估模型落差带来的损耗。
- **演化搜索规模与代价未透明**：32 个提案、596 个开发 episode 的搜索成本、hosted API 调用数与金额在表中为 n/a，**无法评估"演化一次"的真实经济代价**，也难以判断该方法相对"直接多轮试错"的性价比拐点。
- **未报告算力信息**：GPU 型号/数量/时长/显存缺失，RFT 的 LoRA 训练开销亦未披露，**可复现性与能耗对比均不充分**。
- **RFT 证据链薄弱**：54 条接受 / 40 条拒绝决策、24 条训练轨迹、60 个配对 episode，规模过小；且作者自述其非成功率驱动因素，因此"蒸馏可加速"这一结论的外推性有限。
- **校准实验不显著**：测试时适应的一次性校准各方法 p 值均在 0.146–0.791，方向性结论（RACaP 受益、代码生成基线受损）**尚需更大样本确认**。
- **跨具身仍需目标域演化**：冻结 Phase 2 在 Robosuite 仅 17.1%，低于 CaP-X 的 25.7%；RACaP-RS 的 31.4% 依赖域内演化，**"冻结制品直接跨具身"这一更强主张并不成立**。
- **潜在改进方向**（据论文主张可推知）：把演化门控从"配对原生成功严格提升"扩展到多 seed / 多样本以提升统计可靠性；统一演化与评估所用模型以消除混淆；补充真机与更大规模 RFT 数据；公开演化侧算力与成本账本。

## 8. 方法学评价与研究启示

- **主要贡献（概念层面）**：论文把 CaP 的工程痛点重新表述为一个**边界划分问题（evolution-to-execution problem）**，并提出可操作的判据——"跨任务提升成功率的物理机制"进入代码，"场景相关选择"留在 ReAct。这一划分比单纯追求"更强的代码生成"或"更强的 play 目标"更具方法论价值。
- **评价机制的严谨之处**：式(2) 的**配对净增益**（而非绝对成功率）直接奖励泛化性、惩罚对开发集的过拟合；式(3) 的**字典序目标**（先成功、后效率）避免了"更快但更差"的伪改进被采纳；Phase 2 的"单一变更 + 预测增益 + 拒绝条件 + 严格提升才晋升"构成了较完整的自演化护栏。
- **负结果的价值**：RATS play 反而降分（21.1%→11.1%）、RATS-90 接口漂移审计，都是**支持性负证据**，比只报告正向提升的论文更具说服力，也直接论证了"带类型接口 + 回归门控"的必要性。
- **潜在质疑**：
  - 六种 Policy API 的**人工设计成分**（哪些能力该进库、如何暴露参数）在多大程度上可自动化，论文未充分回答；课程 S0–S6 的划分同样带有先验结构。
  - "运行时绝不生成代码"是一条**强约束**，在开放世界任务中出现 API 库未覆盖的新物理机制时，系统只能退化或失败，论文未讨论这类**能力闭包**问题。
  - 公平性控制虽统一了评估模型，但演化侧模型与预算的差异使得"RACaP vs RATS"更像**不同训练范式的比较**，而非受控消融。
- **可迁移的实践原则**：
  1. 把昂贵的搜索/生成移到离线演化阶段，部署期只保留**类型化、可校验的函数调用**；
  2. 对持久化制品（代码、harness、记忆）设置**配对比较 + 严格提升**的晋升门控；
  3. 评估期隔离：隐藏原生谓词、禁止改码、记录调用数/成本/延迟，使结论可审计；
  4. 用"成功优先、效率次之"的字典序目标避免指标被单维度优化。
- **总体判断**：RACaP 在**零样本迁移**与**长时程组合**两个维度上给出了相对代码生成基线的显著且带统计检验的优势，其"演化—执行边界"的框架具有较高的概念清晰度与工程可操作性；但受限于单 seed 的 in-domain 评估、演化/评估模型不一致、算力与演化成本不透明、以及纯仿真验证，其结论的**外部效度仍需独立复现与真机检验**来确认。
