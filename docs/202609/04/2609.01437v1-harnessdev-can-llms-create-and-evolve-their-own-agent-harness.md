## 摘要
随着智能体从研究原型发展为可部署工具，其能力越来越依赖于模型外部的执行基础设施，该基础设施通常被称为智能体执行框架。在固定模型权重的情况下改动该框架会显著改变任务性能。当前的智能体评估通常报告选定框架下的下游性能，而模型自身开发执行框架的能力相对而言尚未得到充分探索。我们提出了HarnessDev基准，该基准将评估单元从任务输出转向可运行基础设施。HarnessDev包含两个阶段：在创建阶段，智能体从最小初始种子和少量用例出发，构建完整的执行系统；在演化阶段，智能体从自身创建的框架出发，利用下游执行反馈迭代修改框架，目标是提升基准性能。我们随后从能力（留出基准上的任务成功率）和效率（执行token成本）两个维度对每个构建得到的框架进行评估。本文报告的创建阶段结果涵盖6个用于创建的大语言模型、4个领域、5个下游基准，共2207个独特下游实例，开发过程中未接触隐藏评估任务。我们发现，生成的框架在代码、搜索与研究领域的表现仍远落后于成熟的人工设计参考框架，而在写作和机器学习实验领域则达到甚至超过了所选参考框架的水平，执行成本存在较大差异。演化阶段带来了一定性能提升，但提升不稳定，且仅能部分迁移到留出任务上。针对固定运行时模型的实验进一步表明，性能提升高度依赖于执行该框架的模型，说明跨模型迁移能力有限。

## Abstract
As agents move from research prototypes to deployed tools, their capability increasingly depends on model-external execution infrastructure, commonly termed the agent harness. Changing this harness while holding model weights fixed can substantially alter task performance. Current agent evaluations typically report downstream performance under a chosen harness, leaving a model's ability to develop the harness itself comparatively underexplored. We introduce HarnessDev, a benchmark that shifts the unit of evaluation from task outputs to runnable infrastructure. HarnessDev covers two stages. In Creation, the agent starts from a minimal seed and a small number of cases, then builds a complete execution system. In Evolution, it starts from its own created harness and iteratively revises it using downstream execution feedback, with the goal of improving benchmark performance. We then evaluate each constructed harness on capability (task success on held-out benchmarks) and efficiency (execution-token cost). The reported Creation results cover six creator LLMs, four domains, and five downstream benchmarks totaling 2,207 unique downstream instances, with hidden evaluation tasks withheld from development. We find that generated harnesses remain substantially behind mature human-engineered references on code and on search and research, while matching or exceeding the selected references on writing and machine-learning experimentation, with large variation in execution cost. Evolution produces some performance gains, but they are unstable and transfer only partially to held-out tasks. Experiments with a fixed runtime model further show that the gains depend strongly on the model executing the harness, indicating limited transfer across models.

# 论文详细总结
## 1. 核心问题与研究背景
- 背景：当前大语言模型智能体已从研究原型走向落地部署，智能体的实际能力高度依赖模型权重之外的外部执行基础设施（即智能体执行框架Agent Harness），负责管理执行循环、工具调用、上下文管理、故障恢复、结果验证等核心逻辑。已有研究显示，固定模型权重更换框架可带来十几个百分点的性能差异，框架对最终能力的影响极大。
- 核心问题：现有智能体评估都默认固定框架，仅评估框架下的任务输出能力，完全没有充分探索大模型自主开发、迭代维护自身执行框架的能力，该领域缺乏标准化的评估基准。

## 2. 提出的方法论
### 核心思想
将评估单元从大模型单次生成的任务输出，转变为大模型构建的可持久化、可运行的执行框架本身，测试大模型开发执行基础设施的能力。
### 关键设计
- 分两大评估阶段：
  1. **创建阶段**：给作为创造者的大模型提供一个极简但可运行的初始种子框架（仅提供基础接口和被动工具，无执行循环、规划、验证、状态管理等核心任务逻辑），搭配少量开发用例和任务规范，要求大模型开发出完整可用的执行框架，开发过程完全隔离隐藏评估任务。
  2. **演化阶段**：创造者大模型基于自身在创建阶段得到的初始框架，利用下游执行反馈，在固定预算内迭代修改优化框架，每一个修改后的版本都会被冻结保留，最终由创造者选出最终版本。
- 双维度评估：
  1. 能力：冻结后的框架在留出测试集上的下游任务成功率，衡量框架的实际效果；
  2. 效率：框架运行下游任务时消耗的执行token数（不计算创建/修改框架消耗的token），衡量框架的运行成本。
- 两种评估设置：
  1. Self-Eval：由创建框架的创造者大模型自身担任执行器，衡量模型与自定义框架的适配效果；
  2. Unified-Eval：所有框架统一使用同一个固定大模型作为执行器，公平对比不同框架本身的质量。

- 整体评价：实验设计分离了创造者与执行器角色，严格隔离开发集与评估集，对所有框架做了合规性审计，控制变量清晰，实验设计客观公平；但演化阶段仅覆盖代码领域，整体样本量有限。

## 6. 主要结论与发现
### 创建阶段结论
1. 性能存在显著的领域差异：大模型生成的框架在写作领域性能接近人工框架，在机器学习实验领域性能超过所选人工参考框架，但在代码、搜索与研究领域，和成熟人工框架仍有较大差距；
2. 随机性与成本差异大：同一模型多次独立生成的框架性能差异明显，不同框架的执行token成本最高相差19倍，且更高的运行成本不对应更好的性能；
3. 跨模型迁移性差：多数生成框架会高度适配创建它的模型，更换执行模型后性能会明显下降。
### 演化阶段结论
1. 增益不稳定且泛化性差：所有创造者都能在可见的反馈开发集上提升性能，但增益在未见过的留出测试集上大幅缩水，演化过程中性能波动大，经常出现修改后性能反而下降的情况；
2. 版本选择能力不足：创作者基于反馈选出的最终版本，很少是留出集上性能最优的版本，容易过拟合反馈集；
3. 增益高度依赖执行模型：只有执行模型和创建者一致时才能获得稳定正增益，更换执行模型后，多数演化结果反而会出现性能下降，跨模型迁移能力非常有限。

## 7. 论文优点
1. 填补领域空白：首次提出了评估大模型自主开发执行框架能力的标准化基准，将评估对象从单次任务输出拓展到可持久化的执行基础设施，更符合实际产业部署的需求；
2. 实验设计严谨：分离了创造者模型和执行器模型的角色，严格隔离开发集与评估集，从能力和效率双维度评估，还额外测试了跨模型迁移性，变量控制清晰，结论可靠；
3. 开放性好：公开了基准项目和所有实验 artifacts，为后续该方向的研究提供了标准化的测试平台。

## 8. 不足与局限
1. 覆盖范围有限：演化阶段目前仅覆盖代码领域，未覆盖另外三个研究领域，基准覆盖不完整；
2. 基线设计存在缺陷：人工参考基线来自不同系统的公开报告，不是统一控制下的配对实验结果，可比性有限；
3. 无法完全分离混淆变量：统一评估设置也无法完全消除框架与执行模型交互的影响，无法完全分离两者对最终性能的贡献；
4. 统计效力不足：演化实验每个设置仅对应一条演化轨迹，样本量小，无法得出统计显著性的结论；
5. 未验证持续演化能力：没有测试演化后的框架能否作为下一轮开发的基础，大模型完全自主持续演化的能力尚未验证；
6. 安全风险：自动生成的框架可能存在不安全代码，虽然研究做了合规审计，但实际部署仍需要额外的严格隔离。
