## 摘要
并行编码智能体可以生成单独有效的补丁，但合并时却会失败。当一个智能体更改了另一个智能体仍然依赖的接口或规则时，就会发生这种情况。我们通过stale这一语义协调基准来研究这些失败。我们的评估对每个补丁单独运行相同的测试，并对其组合运行测试，仅统计由组合补丁引入的失败。我们使用三个层级：具有受控接口更改的合成任务、合并的拉取请求对，以及使用真实Django辅助函数的构造任务。在417个挖掘的Django配对上的834次运行中，在校正评分程序后，只有一个显示出干扰。在使用12个Django辅助函数的构造任务上，97%的运行发生了干扰。一条描述已完成并发更改的消息恢复了82%的运行。即使智能体在使用真实代码的受控任务上失败，已审查的拉取请求也可能包含很少未解决的并行更改。构造的失败率并不能估计这些问题在实践中发生的频率。

## Abstract
Parallel coding agents can produce patches that work alone but fail when merged. This happens when one agent changes an interface or rule that another agent still relies on. We study these failures with stale, a benchmark for semantic coordination. Our evaluation runs the same tests on each patch alone and on their combination, counting only failures introduced by combining the patches. We use three tiers: synthetic tasks with controlled interface changes, pairs of merged pull requests, and constructed tasks that use real Django helpers. Among 834 runs on 417 mined Django pairs, only one showed interference after correcting the grading procedure. On constructed tasks using 12 Django helpers, interference occurred in 97% of runs. A message describing the completed concurrent change recovered 82% of runs. Reviewed pull requests may contain few unresolved parallel changes, even when agents fail on controlled tasks using real code. The constructed failure rates do not estimate how often these problems occur in practice.

# 论文总结：Passes Alone, Fails Together — 并行LLM智能体开发中的语义协调基准测试

## 1. 核心问题与整体含义

- **研究动机**：并行编码智能体（parallel coding agents）各自独立工作时，可以生成单独通过测试的补丁；但当这些补丁合并时，却可能失败。根本原因在于**语义协调（semantic coordination）**问题——一个智能体修改了接口或规则，而另一个智能体仍然依赖旧接口或旧规则。
- **典型场景**：Worker A 添加缓存并修改更新函数以失效缓存；Worker B 在不知情的情况下添加了直接写数据库的批量更新函数，绕过了缓存，导致读取到过期数据。两个补丁在文本层面无冲突（clean merge），但组合后行为错误。
- **核心概念**：
  - **语义协调**：在并发、耦合的变更之间维持一致性，超越无冲突代码合并。
  - **语义协调余量（semantic coordination headroom）**：通过对比“盲并行”（blind）与“知情顺序”（informed/oracle）两种条件下失败数量的差异，估计理想可见性下协调能避免多少失败。
- **整体含义**：版本控制能合并代码，但不能保证行为正确。论文提出 **stale** 基准，系统性地度量“单独通过、合并失败”的现象，并区分“历史已审核 PR”与“受控构造任务”中的干扰率差异。

## 2. 方法论

### 2.1 核心思想

- 对**同一组补丁**，在**相同测试集**下分别运行：
  - **solo**：每个补丁单独应用并测试；
  - **blind**：各智能体在共享基线上独立工作，补丁合并后测试；
  - **informed（oracle）**：智能体按顺序工作，后一个能看到前一个已完成的编辑。
- 只统计**由合并引入的失败**，排除单独补丁本身已存在的失败。

### 2.2 关键公式与指标

- 设 \(F_i\) 为补丁 \(i\) 单独应用时失败的测试集合，\(F_{\text{blind}}\) 为合并后失败的测试集合。
- **干扰度量**：
  \[
  \Delta_{\text{blind}} = F_{\text{blind}} \setminus \bigcup_i F_i
  \]
  即仅在组合时出现的新失败。
- **干扰指示器**：\(I_{\text{blind}} = \mathbb{1}[\Delta_{\text{blind}} > 0]\)。
- **可观测性条件**：一个配对只有在每个智能体的补丁在组合测试套件中通过其自身任务测试时，才被纳入干扰分析。

### 2.3 评分流程

- 丢弃智能体对测试文件的编辑，应用人类 PR 的**gold test patch**。
- 在所有条件下运行**组合测试集**（而非各自任务的测试集），避免因测试集不同造成假干扰。
- 使用 SWE-bench 风格的 fail-to-pass 测试定义正确行为。

### 2.4 三个基准层级

| 层级 | 描述 | 目的 |
|------|------|------|
| **Synthetic（合成）** | 受控接口变更，变化接口数量 \(d \in \{0,...,4\}\) | 隔离“陈旧信息”导致的失败机制 |
| **Mined（挖掘）** | 真实合并 PR 对，共享基线提交 | 检验历史 PR 中是否存在未解决的并行干扰 |
| **Constructed real-derived（构造真实派生）** | 对 12 个真实 Django 辅助函数施加脚本化接口变更 | 验证合成机制在真实代码中是否复现 |

### 2.5 通信条件（comm）

- 向盲智能体发送一条约 130 token 的**oracle 消息**，描述另一个 worker 已完成的变更（如重命名、新增必需参数、返回类型变化）。
- 该消息由脚本化变换生成，代表**完整且准确**的变更描述，用于估计协调余量的上界。

## 6. 主要结论与发现

1. **历史 PR 中干扰极少**：417 对 Django 合并 PR 的 834 次运行中，校正评分后仅 1 例干扰。已审核 PR 可能已在开发/审核过程中解决了并行变更冲突。
2. **合成任务中干扰随陈旧度线性增长**：盲智能体在 \(d\) 个变更接口上全部失败（\(\Delta_{\text{blind}} = d\)，零方差）；知情智能体无失败。
3. **Oracle 消息显著恢复**：合成层干扰从 2.50 降至 0.04（98% 减少）。
4. **构造真实派生任务干扰率高**：12 个 Django 辅助函数上，105/108 次运行（97%）出现干扰；oracle 消息恢复 89/108（82%），干净合并情况下恢复率达 93%。
5. **构造失败率不等于实际发生率**：受控任务故意引入破坏性变更，不能估计日常并行开发中的问题频率或严重性。
6. **返回类型变化最难协调**：即使知情智能体，平均仍有 0.13 次失败/运行。

## 7. 优点

- **问题定义清晰**：将“语义协调”从“文本合并冲突”中分离出来，提出可量化的干扰度量 \(\Delta_{\text{blind}}\) 和协调余量概念。
- **评分程序严谨**：发现并纠正了“不同测试集导致假干扰”的陷阱，强调所有条件使用相同组合测试集。
- **三层基准设计**：合成层隔离机制、挖掘层检验历史、构造层验证真实代码，层次分明。
- **确定性挖掘流水线**：共享基线检查、干净合并过滤、基线有效性验证，可复现性强。
- **多维度验证**：多模型、多框架、多仓库、不相交控制组，增强结论可信度。
- **诚实的局限性讨论**：明确指出构造失败率不能外推为实际发生率，避免过度解读。

## 8. 不足与局限

- **仓库覆盖有限**：智能体实验仅限 Django；其他仓库仅用于挖掘验证，未进行智能体求解。
- **构造任务的人为性**：脚本化破坏性变更与真实开发中的渐进式变更不同，可能高估干扰率。
- **Oracle 消息的理想化**：通信条件假设完整、准确的已完成变更描述，未测试计划、未完成补丁或自动摘要等现实场景。
- **仅两两配对**：未研究 \(N > 2\) 的多任务场景，其中可能出现三路以上才触发的失败。
- **测试覆盖依赖**：干扰度量依赖 gold tests，测试遗漏的缺陷无法被检测；多个测试可能检测同一缺陷，计数解释需谨慎。
- **历史 PR 的选择偏差**：已审核 PR 可能已解决冲突，导致挖掘层干扰率被低估；未审核的并行工作记录缺失。
