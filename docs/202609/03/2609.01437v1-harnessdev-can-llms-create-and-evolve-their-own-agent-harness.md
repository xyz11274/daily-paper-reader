## 摘要
随着智能体从研究原型走向部署工具，其能力越来越依赖于模型外部的执行基础设施，即通常所说的智能体框架（agent harness）。在固定模型权重的情况下修改该框架会大幅改变任务性能。当前的智能体评估通常报告选定框架下的下游性能，而模型自主开发框架的能力相对而言鲜有探索。我们提出HarnessDev，这是一个将评估单元从任务输出转向可执行基础设施的基准测试。HarnessDev包含两个阶段：在创建阶段，智能体从最小种子和少量用例出发，构建出完整的执行系统；在演化阶段，智能体从自身创建的框架出发，利用下游执行反馈迭代修订框架，以提升基准性能为目标。随后我们会从能力（留存测试基准上的任务成功率）和效率（执行令牌成本）两个维度评估每个构建出的框架。本文报告的创建阶段结果涵盖6个创建大语言模型、4个领域、5个下游基准，总计2207个独特下游实例，开发过程中对评估任务做了隐藏处理。我们发现，生成的框架在代码、搜索与研究领域的表现远落后于成熟的人工设计参考框架，而在写作和机器学习实验领域则能达到甚至超过所选参考框架，不过执行成本差异很大。演化确实能带来一定性能提升，但提升不稳定，且仅能部分迁移到未见过的任务上。针对固定运行时模型的实验进一步表明，性能提升高度依赖于执行框架的模型，说明跨模型迁移能力有限。

## Abstract
As agents move from research prototypes to deployed tools, their capability increasingly depends on model-external execution infrastructure, commonly termed the agent harness. Changing this harness while holding model weights fixed can substantially alter task performance. Current agent evaluations typically report downstream performance under a chosen harness, leaving a model's ability to develop the harness itself comparatively underexplored. We introduce HarnessDev, a benchmark that shifts the unit of evaluation from task outputs to runnable infrastructure. HarnessDev covers two stages. In Creation, the agent starts from a minimal seed and a small number of cases, then builds a complete execution system. In Evolution, it starts from its own created harness and iteratively revises it using downstream execution feedback, with the goal of improving benchmark performance. We then evaluate each constructed harness on capability (task success on held-out benchmarks) and efficiency (execution-token cost). The reported Creation results cover six creator LLMs, four domains, and five downstream benchmarks totaling 2,207 unique downstream instances, with hidden evaluation tasks withheld from development. We find that generated harnesses remain substantially behind mature human-engineered references on code and on search and research, while matching or exceeding the selected references on writing and machine-learning experimentation, with large variation in execution cost. Evolution produces some performance gains, but they are unstable and transfer only partially to held-out tasks. Experiments with a fixed runtime model further show that the gains depend strongly on the model executing the harness, indicating limited transfer across models.

## 1. 论文核心问题与研究背景
- 当前大语言模型智能体从研究原型走向落地部署，其实际能力高度依赖模型外部的执行基础设施，即**智能体框架（agent harness）**；在模型权重固定的情况下，更换不同的框架可使任务性能产生十几个百分点的显著差异。
- 现有智能体评估普遍只关注固定框架下模型的下游任务表现，从未探索大语言模型自主开发、迭代自身执行框架的能力，这一领域存在明显评估空白。
- 本文的核心目标就是测试大语言模型能否自主创建并持续演化出可用的智能体框架，填补这一评估空白。

## 2. 方法论
### 核心思想
将智能体评估的单元从**单轮任务输出**转向**持久可运行的执行基础设施（即智能体框架本身）**，从创建和演化两个阶段评估大模型开发框架的能力，从能力和效率两个维度评估生成框架的质量。

### 关键设计细节
- **评估流程分为两个阶段**：
  1. **创建阶段**：给大模型（Creator，负责开发框架）提供一个最小可运行的「弱种子」框架（仅提供基础接口，无任何任务执行策略，未修改时得分恒为0），加上少量开发用例，要求Creator从零构建出完整的可运行任务框架，构建完成后冻结框架。
  2. **演化阶段**：Creator基于自己在创建阶段得到的初始框架，利用下游执行反馈，持续迭代修订框架，目标是提升下游性能，每次迭代生成的有效框架都需要冻结版本。
- **评估设置**：分离Creator（开发框架的模型）和Executor（运行框架执行下游任务的模型）两种角色，设置两种评估模式：
  1. **Self-Eval**：Creator同时作为Executor，评估Creator适配自身能力开发的框架的整体表现，符合实际部署场景。
  2. **Unified-Eval**：固定同一个Executor运行所有生成框架，消除Executor能力差异的影响，公平对比不同框架本身的质量。
- **评估指标**：
  1. **能力**：冻结框架在隐藏的held-out下游任务上的成功率，衡量框架的泛化效果。
  2. **效率**：框架运行下游任务消耗的Executor token数量（不统计Creator开发框架消耗的token），衡量部署成本。
- **框架要求**：生成的框架必须实现六个核心模块：执行循环、工具调度策略、上下文管理、状态与记忆、生命周期与故障恢复、结果验证。

## 3. 实验设计
- **覆盖领域与基准**：覆盖4个领域，共5个下游基准，总计2207个独特下游实例，开发过程中对评估任务做了隐藏处理：
  1. 代码领域：SWE-bench Pro（731个任务）、Terminal-Bench 2.1（89个任务）
  2. 数据分析（机器学习实验）领域：MLE-bench（75个任务）
  3. 写作领域：EQ-Bench3（46个任务）
  4. 搜索研究领域：BrowseComp（1266个任务）
- **对比对象**：生成框架分别与弱种子框架、成熟的人工设计参考框架对比。
- **测试模型**：创建阶段测试了6个主流前沿大模型作为Creator：Opus 4.8、GPT-5.5、Gemini 3.1 Pro、DeepSeek V4 Pro、Qwen 3.7 Max、Seed 2.0 Pro。
- **实验分组**：
  1. 创建阶段：每个Creator-基准对独立创建3次框架，取平均结果，同时做Self-Eval和Unified-Eval两种评估。
  2. 演化阶段：目前仅聚焦代码领域，Creator基于自身创建的初始框架开展演化，分Self runtime（Creator自身作为Executor）和Fixed Gemini runtime（固定Gemini作为Executor）两种设置，每次迭代的有效版本都在反馈开发集和隐藏held-out集分别评估。

## 5. 实验数量与充分性
- 创建阶段：共6个Creator模型 × 5个下游基准 × 3次独立创建 = 90次独立框架构建，加上两种评估设置，总计约180次评估，样本量足够。
- 演化阶段：共产生9条演化谱系（5条Self runtime，4条Fixed Gemini runtime），得到73个经过官方评估的冻结框架版本，每个版本都在开发集和held-out集分别评估。
- 整体来看，实验设计客观严谨，分离了开发集和评估集，控制了变量，Creation实验充分；Evolution目前仅覆盖代码领域，样本量和覆盖范围还有提升空间。

## 6. 主要结论与发现
### 创建阶段结论
- 当前大模型可以从零构建出可运行的智能体框架，但性能存在显著领域差异：写作领域生成框架接近人工参考水平，机器学习实验领域甚至超过所选人工参考，但代码、搜索研究领域和成熟人工框架仍有很大差距。
- 同一模型多次独立创建的框架性能差异也很大，更高的执行token成本不代表更好的性能，不同框架的执行成本差异最高可达十九倍。
- 生成的框架通常和创建它的Creator模型高度适配，更换Executor后性能往往大幅下降，跨模型迁移能力有限。

### 演化阶段结论
- 所有Creator都能在开发反馈集上获得性能提升，但增益迁移到隐藏held-out集后会大幅缩水。
- 演化过程性能不稳定，不是单调提升，Creator根据开发反馈选择的最终版本通常不是held-out集上的最优版本，容易过拟合到开发反馈集。
- 演化得到的性能增益高度依赖执行框架的模型，只有Opus 4.8在固定Executor下仍能获得held-out性能提升，其他模型更换Executor后性能反而下降，进一步说明跨模型迁移能力有限。

## 7. 论文亮点
- 首次提出针对大语言模型自主开发智能体框架能力的标准化基准，将智能体评估从「固定框架下的任务求解能力」拓展到「自主开发执行基础设施的能力」，填补了领域空白，开辟了新的研究方向。
- 实验设计严谨科学：分离Creator和Executor两种角色，区分开发集和隐藏held-out评估集，设计两种互补的评估模式，既符合实际部署场景，又能公平对比框架本身质量。
- 同时从能力和效率两个维度评估框架，兼顾了任务效果和实际部署的成本因素，评估更全面。
- 演化阶段对每个迭代版本都做完整评估，明确区分开发反馈增益和held-out泛化增益，能准确反映大模型真实的演化能力。

## 8. 不足与局限
- 演化阶段目前仅覆盖代码领域，写作、数据分析、搜索研究等领域尚未开展实验，领域覆盖不完整。
- 人工参考基线是公开的系统级结果，不是统一Executor下的配对控制实验，对比存在一定偏差。
- Evolution中每个Creator-runtime组合仅对应一条演化轨迹，样本量不足，无法支撑统计显著性推断。
- 演化阶段的held-out评估仅覆盖SWE-Pro，未覆盖Terminal-Bench，结论的普适性有限。
- 未探索演化得到的框架能否作为新的开发环境支撑进一步演化，这一问题留待后续研究。
